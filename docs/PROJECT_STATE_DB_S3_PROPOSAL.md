# Предложение: Postgres + S3 как SSOT вместо файла на Google Drive

**Статус:** ПРЕДЛОЖЕНИЕ, не реализовано. Держим текущую схему (Drive = SSOT,
см. [`FOLDER_STATE_SSOT_PLAN.md`](./FOLDER_STATE_SSOT_PLAN.md)) до отдельного
решения — клиент сейчас явно просит Google Drive, и десктоп-приложение уже
умеет читать/писать `folderState.json` там. Этот документ — на будущее: если
появится окно на пересмотр архитектуры (или клиент сам придёт к тому же
выводу), здесь готовый план, с чего начинать.

## Позиция

Файл в облачном хранилище (`options/folderState.json` + `gsync`) в роли
единственного источника правды — рабочее, но структурно менее надёжное
решение, чем связка "своя БД (Postgres) как SSOT + S3 для бинарных файлов".
Ниже — почему, и как это можно сделать, не потеряв то, что уже работает.

---

## Проблемы модели "файл = SSOT" (технически, не в порядке важности)

1. **Нет транзакций и atomic compare-and-swap.** `folderState.json`
   перечитывается, патчится в памяти и перезаписывается целиком
   (read-modify-write, см. `lib/project-drive.ts:setProjectAutomationEnabled`).
   Между чтением и записью — окно для гонки: два клиента (сайт + десктоп,
   или две машины) могут одновременно решить, что их версия правильная.
   `updatedAt`/LWW в плане — это смягчение, не устранение гонки.

2. **`gsync` — не merge-движок.** Сам план это прямо признаёт
   ("Известное ограничение"): если два инстанса пишут один файл в одном окне
   синхронизации, получаем перезапись одной версии другой или
   `folderState (conflicted copy).json`. На Postgres такого класса багов
   не существует — сериализуемость даёт СУБД.

3. **Задержка и неопределённость доставки.** Изменение из десктоп-приложения
   видно сайту только когда: (а) gsync успел синхронизировать файл в облако,
   (б) сайт следующий раз *перечитал* Drive (сейчас — только при заходе на
   `/account/projects/[id]`, то есть по факту "когда пользователь зашёл и
   обновил страницу"). Это не push, это poll-по-требованию. Обратное — сайт
   → десктоп — зависит от того, как часто десктоп перечитывает файл.

4. **Google Drive API — это лимиты и латентность, а не БД.** Каждое чтение
   `folderState.json` — это list children + find child by name + download
   text file (см. `loadProjectDriveState`), т.е. 3+ round-trip к Google на
   один проект. Показать статус для списка из N проектов без N×3 запросов
   нельзя — поэтому сейчас статус в списке идёт из кэша в Postgres, а не из
   Drive напрямую (уже частичное признание, что Drive плохо подходит для
   "быстро отдать текущее состояние").

5. **Нет схемы, нет constraint'ов, нет queries.** "Покажи все проекты,
   выключенные автоматически более 30 дней назад" — на файлах это скачать и
   распарсить N файлов; в Postgres — один `SELECT` с индексом.

6. **Нет аудита из коробки.** Файл хранит только последнее состояние
   (`updatedAt`/`updatedBy`), история изменений не хранится. В Postgres
   тривиально завести append-only таблицу событий.

7. **Файл может быть повреждён/отсутствовать.** JSON, руками правленный или
   недописанный при сбое середины `gsync`, — `parseFolderState` в текущем
   коде уже defensively на это рассчитан (`null`-фоллбеки), но это защита от
   симптома, не от причины.

Ничего из этого не значит, что текущая реализация плохая — план в
`FOLDER_STATE_SSOT_PLAN.md` разумно смягчает почти все эти риски (LWW по
`updatedAt`, merge=max для активности, троттлинг записи, guard на
воскрешение папки). Но это именно смягчение симптомов файловой модели, а не
устранение класса проблем.

## Целевая архитектура

```
┌─────────────┐       REST/webhook         ┌──────────────────┐
│ Desktop app │ ───────────────────────▶   │   Postgres (SSOT) │
│ (Tauri)     │ ◀─────────────────────—    │  projects, media,  │
└─────────────┘     poll / push notify     │  status, events    │
       │                                    └──────────────────┘
       │ presigned PUT/GET                          │
       ▼                                             ▼
┌─────────────┐                             ┌──────────────────┐
│  S3-совм.   │                             │   Next.js сайт    │
│  storage    │ ◀────── читает/пишет ─────▶ │  (личный кабинет) │
└─────────────┘                             └──────────────────┘
       │
       ▼ (опционально, для клиента)
┌─────────────┐
│ Google Drive│  ← односторонняя копия/экспорт, не участвует
│  (mirror)   │    в принятии решений
└─────────────┘
```

Ключевая идея: **Postgres — единственный владелец истины** про
`enabled/disabled`, метаданные проекта и список файлов. Google Drive (пока
он нужен клиенту) становится *потребителем* этой правды и *витриной* для
файлов, а не местом, где она вычисляется.

### Что уже есть в репозитории и можно переиспользовать

В проекте уже есть рабочая, протестированная S3-инфраструктура — она
сейчас используется для медиа `admin`-контента и вложений `feature
suggestions`, но не для проектных файлов кабинета:

- [`lib/s3-client.ts`](../lib/s3-client.ts) — `getS3Client()`, уже настроен
  под S3-совместимые провайдеры (path-style, отключены flexible checksums —
  см. комментарий про баг с presigned PUT).
- [`lib/s3-config.ts`](../lib/s3-config.ts) — префиксы ключей, публичные URL,
  `/api/media/[...key]` проксирование приватного бакета.
- [`lib/attachment-public-url.ts`](../lib/attachment-public-url.ts) —
  презайненные GET-ссылки с TTL для внешних сервисов.
- `scripts/s3-*.mjs` — проверка presigned upload, CORS, префиксов на живом
  бакете.
- Пример presign-flow для загрузки: [`app/api/admin/upload/presign/route.ts`](../app/api/admin/upload/presign/route.ts).

Т.е. переезд media-загрузок проекта с Drive на S3 — это в основном
переиспользование существующего кода, не написание нового слоя с нуля.

## Модель данных (Postgres, эскиз)

Заменить одинокий `is_active BOOLEAN` на что-то по форме близкое к
`folderState.json`, но живущее в БД как SSOT, плюс журнал событий:

```sql
-- Заменяет/расширяет projects.is_active. schema_version — на будущее,
-- если формат состояния будет меняться.
ALTER TABLE projects ADD COLUMN IF NOT EXISTS automation_enabled BOOLEAN NOT NULL DEFAULT TRUE;
ALTER TABLE projects ADD COLUMN IF NOT EXISTS automation_disabled_reason TEXT; -- 'manual' | 'auto' | NULL
ALTER TABLE projects ADD COLUMN IF NOT EXISTS automation_disabled_at TIMESTAMPTZ;
ALTER TABLE projects ADD COLUMN IF NOT EXISTS automation_updated_by TEXT; -- 'site:<email>' | 'app:<clientId>' | 'system:auto'
ALTER TABLE projects ADD COLUMN IF NOT EXISTS last_activity_at TIMESTAMPTZ;
ALTER TABLE projects ADD COLUMN IF NOT EXISTS storage_backend TEXT NOT NULL DEFAULT 'drive'; -- 'drive' | 's3' | 'dual' — миграция по проекту, не всем сразу

-- Аудит: append-only, никогда не UPDATE/DELETE.
CREATE TABLE IF NOT EXISTS project_status_events (
  id           TEXT PRIMARY KEY,
  project_id   TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  enabled      BOOLEAN NOT NULL,
  reason       TEXT,               -- 'manual' | 'auto' | NULL
  actor        TEXT NOT NULL,      -- кто изменил
  source       TEXT NOT NULL,      -- 'site' | 'desktop-app' | 'drive-sync'
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Файлы проекта, если бэкенд — s3 (параллельно project_media, который сейчас про Drive):
CREATE TABLE IF NOT EXISTS project_files_s3 (
  id            TEXT PRIMARY KEY,
  project_id    TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  object_key    TEXT NOT NULL,     -- ключ в S3, buildS3ObjectKey()
  file_name     TEXT NOT NULL,
  mime_type     TEXT NOT NULL,
  size_bytes    BIGINT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`storage_backend` на уровне проекта (а не глобальный флаг) — чтобы миграцию
можно было катить постепенно, проект за проектом, а не всем клиентам сразу.

## Как быть с десктоп-приложением

Это главное ограничение: десктоп-приложение (отдельный репозиторий, Tauri)
**сейчас читает правду из файла на Drive**, не из HTTP API. Полный переход
на Postgres как SSOT требует, чтобы десктоп тоже стал говорить с сайтом
напрямую (или хотя бы с БД через API) — а это отдельный релиз приложения,
не то, что можно сделать только правками в этом репозитории.

Поэтому реалистичный путь — не "выключить Drive одним PR", а **мост**,
который постепенно меняет, кто на самом деле принимает решение:

### Фаза 0 (сейчас, уже сделано)
Drive = SSOT, Postgres = кэш горячего пути для списков в кабинете.
См. `FOLDER_STATE_SSOT_PLAN.md` и текущую реализацию
(`lib/project-drive.ts`, `/api/projects/[id]/drive/folder-state`).

### Фаза 1 — Postgres становится SSOT для *сайта*, Drive — для десктопа
Ничего не меняем в контракте файла и в десктоп-приложении. На сайте:
- Тумблер в кабинете пишет **сразу в Postgres** (`automation_enabled` +
  строка в `project_status_events`) и **синхронно пытается** отразить это в
  `folderState.json` (как сейчас) — но при конфликте/ошибке Drive-записи
  **выигрывает Postgres**, а не наоборот. Т.е. меняем приоритет LWW: сегодня
  файл главный и БД догоняет; здесь БД главная и файл догоняет.
- Чтение из Drive (`loadProjectDriveState`) остаётся, но теперь это просто
  "что видит десктоп-приложение" — источник для примирения, не для истины.

### Фаза 2 — Drive push вместо poll-по-требованию
Вместо "перечитываем файл только когда пользователь зашёл на страницу
проекта" — подписаться на изменения через
[Drive API `watch`/push notifications](https://developers.google.com/workspace/drive/api/guides/push)
(нужен верифицированный домен и HTTPS-эндпоинт для вебхука) или хотя бы
периодический фоновый job (cron/queue), который поллит все `driveFolderId`
пользователей и льёт изменения в `project_status_events`. Уже сейчас можно
завести это как отдельный воркер, не трогая основной запрос страницы.

### Фаза 3 — Медиа-файлы: S3 как основное хранилище
Новые загрузки в кабинете идут в S3 (переиспользуя presign-flow, который
уже есть для admin/feature-suggestions), `project_files_s3` — таблица
истины. Если `storage_backend = 'dual'` для проекта — дополнительно кладём
копию в Drive-папку клиента (асинхронно, через ту же очередь, что и в Фазе
2), чтобы клиент продолжал видеть файлы у себя в Drive без переобучения.

### Фаза 4 — Десктоп-приложение говорит с сайтом напрямую
Отдельный релиз десктопа: вместо чтения/записи `folderState.json` он дёргает
API сайта (или напрямую БД через защищённый канал) за `enabled` и активностью.
На этом этапе Drive-файл можно оставить только как read-only витрину для
клиента (генерируется сайтом, никто его больше не парсит как источник
правды) — или убрать совсем, если клиент согласится.

Фазы 0–2 не требуют изменений в десктоп-приложении и можно катить только
правками в этом репозитории. Фазы 3–4 требуют координации (S3-бакет,
доступы, возможно — согласие клиента на смену хранилища файлов).

## Открытые вопросы

- **Кто оплачивает и администрирует S3-бакет** (у клиента уже есть один,
  судя по `AWS_S3_BUCKET`/`AWS_ENDPOINT_URL` в `.env` — уточнить, тот же
  бакет или отдельный префикс/бакет под проектные файлы).
- **Drive push notifications** требуют верифицированный домен в Google
  Cloud Console и HTTPS webhook-эндпоинт с определённым SLA ответа — нужно
  на это время/доступ до Фазы 2, иначе там остаётся polling by cron.
  сейчас не блокер, но не бесплатно по времени.
- **Формат конфликтов сайт vs. десктоп во время Фазы 1.** Пока десктоп не
  переехал на API (Фаза 4), он продолжает писать в файл, а сайт — в
  Postgres первым делом; нужно явное правило, кто "выигрывает" при
  одновременном изменении (предлагаю: `updatedAt` сервера Postgres — как
  и сейчас для правок с сайта, только теперь единая шкала времени для всех
  источников, не только для сайта).
- **Нужно ли клиенту вообще продолжать видеть файлы в Drive после Фазы 3**,
  или "клиент просит Drive" относится только к текущему воркфлоу
  десктоп-приложения, а не к папке кабинета конкретного пользователя —
  стоит прямо спросить, чтобы не тащить dual-write, если не нужно.

## Что не делаем сейчас

Ничего из этого не трогает существующий Drive-flow. `is_active` в БД
остаётся кэшем `folderState.enabled`, как реализовано сегодня. Этот файл —
справочник на будущее, план начинать с Фазы 1 (она самая дешёвая и не
требует релиза десктоп-приложения), когда будет решение двигаться в эту
сторону.
