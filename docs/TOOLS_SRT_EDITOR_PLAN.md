**Расхождения с §15.2, зафиксированные сознательно.** Аудио дорожек играется через `<audio>`

переключишь язык. Раскладку можно переназначить в настройках инструмента; она хранится в
`localStorage` вместе с остальным видом.

## 0. Зачем этот инструмент

На входе — один аудиофайл с несколькими персонажами. Обработка разделяет его на
дорожки по персонажам, из каждой делает SRT и переводит. Дальше нужен человек:
проверить распознанный текст, поправить тайминги, перенести титры, которые
автоматика приписала не тому персонажу, вычитать перевод.

Сейчас это делать негде. Инструмент — рабочее место для этого шага: видео,
таймлиния с дорожками персонажей, список титров «оригинал ↔ перевод». Результат
складывается в структуру, которую потом откроет следующий инструмент (озвучка) —
он ещё не спроектирован, поэтому формат результата должен быть самодостаточным и
читаемым без нашего кода.

**Границы:** инструмент **не** озвучивает, **не** переводит (перевод приходит
готовым от обработки), **не** рендерит видео. Он правит черновик титров.

## Часть 0. Решения, зафиксированные владельцем

| Решение | Следствие |
|---|---|
| Вкладка «Инструменты» переиспользуется под список инструментов | `group_name='tools'` у проектов становится legacy: в UI больше не используется, значение в БД не трогаем |
| Структура папки `OUT` настраивается графом обработки (нодами) и может быть любой | Раскладку из §8 считаем **контрактом**, который владелец настроит в графе; инструмент дополнительно умеет читать нестандартную раскладку по шаблону |
| У инструмента **свои** настройки, не связанные с `options.json` проекта | С обработкой инструмент связан только двумя вещами: проектом (откуда берём папки) и раскладкой внутри `OUT`. Ничего из `options.json` он не читает и не пишет — §9 |
| Перевод уже лежит в папке готовым | Колонка перевода **отображает и даёт править**; интеграции с API перевода в v1 нет |
| **Инструмент на сайте работает только онлайн** | Ничего не скачиваем, ничего не синхронизируем: папка проекта в R2 — единственное место, где лежат файлы. Отпадают локальное зеркало, очередь отправки, гибридный режим и браузерная матрица |
| **Локальная работа — отдельный редактор в программе** | Не адаптер и не режим этого инструмента, а своя реализация в `fs.manager.tauri` со своим интерфейсом и своим доступом к файлам. Обе стороны не знают друг о друге |
| **Общего кода интерфейса не будет: сайт на Tailwind/Radix, программа на MUI** | Внешний вид у них разный намеренно — инструмент должен выглядеть как то приложение, в котором открыт. Значит две реализации представления |
| **Сначала сайт, потом программа по этому документу** | Порядок выбран владельцем: сперва рабочая версия на сайте, документ доводится до уровня реализации, вторая версия пишется по нему. Отсюда §20 (что переносится как есть) и §21 (порядок портирования) |
| **Общий у них только формат документа** | [DIALOG_FORMAT.md](./DIALOG_FORMAT.md) — контракт, а не код. Правки согласовываются в двух зеркальных документах, как уже сделано с описанием проекта |
| **Источник правды — не SRT, а свой документ `dialog.json`** | Формат под нашу задачу: дорожки, реплики, переводы, статусы, задел под озвучку. SRT / VTT / формат для Reaper — экспорт из документа |
| **Вся обработка идёт на локальных машинах; сайт только формирует задание** | Инструмент привязан **только к структуре в `OUT`**. Промежуточные файлы (аудио 16 кГц, `words.json`, разметка спикеров) живут в локальной рабочей папке несколько дней и вычищаются: ни в онлайн-хранилище, ни в `OUT` их нет. Значит `dialog.json` обязан быть самодостаточным |
| **Дорожка персонажа — это его титры; отдельное аудио не требуется** | Достаточно одного общего звука (дорожка видео) и титров по персонажам. Разделять звук по персонажам ради редактора не нужно; если стемы всё же есть — они просто заполняют поля документа. Звука нет вовсе — инструмент всё равно работает: тайминги и текст правятся |
| **Целевая точность автоматики — ~70 %** | Инструмент существует, чтобы человек добирал остальное. Приоритет не «меньше ошибок автоматики», а «ошибка видна и правится одним движением»: дорожка «не распознано», сортировка по уверенности, перенос реплики drag'ом |

# Часть I. Раздел «Инструменты»

## 1. Что показывает вкладка ✅

Вкладка `?tab=tools` в кабинете ([workspace-shell.tsx:59](../components/account/workspace-shell.tsx#L59))
перестаёт показывать проекты и показывает **инструменты пользователя** — только
те, которые он себе добавил.

- Пусто → плашка `emptyTools` + кнопка «Добавить инструмент» по центру.
- Кнопка «Добавить инструмент» в шапке раздела — на том же месте, где «Новый
  проект» в упрощённом режиме ([simple-mode.tsx:310](../components/account/workspace/simple-mode.tsx#L310)).
- Сетка карточек, порядок — пользовательский (drag, `@dnd-kit` уже в проекте).

**Карточка экземпляра инструмента:**

| Элемент | Поведение |
|---|---|
| Иконка + тип-тег | из реестра (§3) |
| Имя | своё, переименовываемое (по умолчанию — имя из реестра) |
| Подключённый источник | «Проект / OUT / clip_042» или «не подключён» |
| Статус | «папка недоступна», «есть несохранённые правки», «новые файлы в папке» |
| Открыто | относительное время последнего открытия |
| Действия | Открыть · Настройки · Дублировать · Удалить |

Один и тот же инструмент можно добавить **несколько раз** — это разные
экземпляры с разными источниками и настройками. Так переводчик держит рядом
«онлайн-проект клиента А» и «локальную папку по NDA» без перенастройки.

## 2. Модалка «Добавить инструмент» ✅

Отдельное модальное окно (`components/ui/dialog`), каталог всех доступных
инструментов с настройками по умолчанию.

- **Теги-фильтры сверху** — по типу материала: `srt`, `text`, `video`, `image`,
  `audio`, `data`. Мультивыбор, «Все» по умолчанию. Тег = поле `kinds` в реестре,
  а не свободный текст.
- **Поиск** по имени и описанию.
- **Карточка каталога:** иконка, имя, одно-два предложения описания, теги,
  кнопка «Добавить». После добавления — модалка закрывается, карточка появляется
  в сетке, сразу открывается диалог «Подключить источник» (§6).
- Инструменты, которые ещё не готовы, показываются с бейджем «скоро» и
  неактивной кнопкой — так раздел не выглядит пустым на старте.

## 3. Реестр инструментов — код, не БД ✅

```ts
// lib/tools/registry.ts
export type ToolKind = "srt" | "text" | "video" | "image" | "audio" | "data"

export type ToolDefinition = {
  key: "srt-editor"                 // стабильный ключ, попадает в БД
  kinds: ToolKind[]                 // теги в модалке
  titleKey: keyof Dictionary        // имя из словаря, не литерал
  descriptionKey: keyof Dictionary
  icon: LucideIcon
  status: "ready" | "soon"
  defaults: ToolSettings            // настройки по умолчанию
}
```

Каталог в БД не нужен: у инструмента есть UI, значит появление нового
инструмента — это всё равно деплой. Таблица бы только добавила расхождение
между «есть запись» и «есть код».

```sql
CREATE TABLE IF NOT EXISTS user_tools (
  id             TEXT PRIMARY KEY,
  user_id        TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  tool_key       TEXT NOT NULL,
  title          TEXT NOT NULL DEFAULT '',
  settings       JSONB NOT NULL DEFAULT '{}'::jsonb,
  source         JSONB NOT NULL DEFAULT '{}'::jsonb,
  sort_order     INTEGER NOT NULL DEFAULT 0,
  last_opened_at TIMESTAMPTZ,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  deleted_at     TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS user_tools_owner_idx
  ON user_tools (user_id, sort_order) WHERE deleted_at IS NULL;
```

`source` для локального режима **не хранит путь к файлам** — только метку
(`{"mode":"local","label":"Рабочая папка"}`); сам доступ к папке живёт в
`IndexedDB` браузера (`FileSystemDirectoryHandle`). Это прямое следствие NDA:
на сервер не уходят даже имена папок.

**API:**

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/account/tools` | список экземпляров пользователя |
| `POST` | `/api/account/tools` | добавить экземпляр (`{ toolKey }`) |
| `PATCH` | `/api/account/tools/[id]` | имя, настройки, источник, порядок |
| `DELETE` | `/api/account/tools/[id]` | soft-delete |

Схемы — `zod`, рядом с остальными (`lib/tool-schemas.ts`), словарь — в
[components/account/i18n.tsx](../components/account/i18n.tsx), проверка
`npm run i18n:check`.

## 5. Роутинг ✅

- `/account/projects?tab=tools` — список инструментов.
- `/account/projects?tab=tools&tool=<instanceId>` — открытый инструмент.

**Сделано иначе, чем планировалось, и вот почему.** В плане был отдельный роут
`/account/tools/[instanceId]`. На практике инструмент открывается в том же шелле
и в той же области, что проект: боковое меню обязано остаться на месте (это
требование владельца), а в полном режиме нужна ещё и колонка со списком слева —
то есть ровно раскладка раздела проектов. Отдельная страница означала бы копию
этой раскладки, а на глубокую ссылку это не влияет: `?tab=tools&tool=<id>`
работает так же.

Параметр именно `tool`, а не `id`: `?id=` занят выбранным проектом, и рабочая
область попыталась бы открыть проект с идентификатором инструмента.

Состояние внутри инструмента (какая задача открыта) пока живёт в БД — в
`user_tools.source`, а не в URL. Ссылку «открой мне вот эту задачу» вернём, когда
появится сам редактор: тогда в адрес добавится и позиция курсора.

## 7. Инструмент на сайте — только онлайн ⬜

Файлы лежат в папке проекта в R2 и никуда не копируются. Ни локального зеркала,
ни синхронизации, ни очереди отправки, ни выбора папки на диске.

| что | как |
|---|---|
| видео и аудио | стримом: подписанный GET + Range-запросы, перемотка без скачивания файла |
| `dialog.json` | читается при открытии, пишется по `ifMatch` (§10) |
| SRT-сырьё, пики | обычный GET, кэширование — штатным HTTP-кэшем браузера |
| экспорт | `presign` → PUT → `notify` в ту же папку |
| незаписанные правки | журнал операций в IndexedDB — **только** восстановление после падения браузера, не файловый кэш (§10) |

Работает в любом браузере: ничего, кроме `fetch`, `<video>` и `IndexedDB`, не нужно.

### Почему локальной работы здесь нет

Разобрано и закрыто. Локальный режим в браузере означал бы File System Access API
(только Chromium, разрешение заново после каждого перезапуска) или локальный
HTTP-мост из программы (Safari режет как mixed content, Chrome требует
preflight-заголовков Private Network Access). Это не «универсальный инструмент»,
а три разных полурешения с разными дырами, каждое со своей реализацией доступа к
файлам.

**Локальная работа живёт в программе** — там, где файловый доступ уже есть, всё
равно нужен для NDA-контура (материал не покидает сеть клиента) и не зависит от
браузера: `fs.manager.tauri`, план `ideasAndTest/DIALOG_EDITOR_PLAN.md`.

### Цена решения, названная прямо

Редактор существует дважды, и две реализации друг о друге не знают: правку
поведения придётся вносить в двух местах руками. Это осознанная цена, а не
недосмотр — ровно тот же выбор, что уже сделан в проекте дважды:

- [PROJECT_OPTIONS_PANEL.md §1](./PROJECT_OPTIONS_PANEL.md) — редактора графа на
  сайте не будет, синхронизируется контракт, а не код;
- [lib/pipeline/process-queue.ts](../lib/pipeline/process-queue.ts) — порт
  десктопного движка очереди, дублирование сознательное и задокументированное;
- описание проекта — [DESCRIPTION_FORMAT.md](./DESCRIPTION_FORMAT.md): один
  формат, два независимых редактора (Tiptap в программе, react-markdown на сайте).

**Что снижает цену дублирования:**

1. **Формат — единственный контракт.** Он вынесен в отдельный документ с
   правилами, эталонным файлом и проверкой «открыл → сохранил → файл побайтово
   тот же» ([DIALOG_FORMAT.md §10](./DIALOG_FORMAT.md)). Расходится не поведение
   кнопок, а только оно — и это видно сразу.
2. **Чистая логика может быть общей, UI — нет.** Обе стороны на TypeScript, и
   разбор документа, валидация, слияние и экспортёры — функции без зависимостей и
   без DOM. Их разумно держать одной копией и копировать скриптом со сверкой (в
   программе такой приём уже есть: `npm run masks:docs` предупреждает о
   расхождении дублей). Компоненты интерфейса не переносятся: MUI против
   Tailwind — см. §V.7.
3. **Расходиться в UI — нормально.** На сайте это вкладка в кабинете с мышью и
   широким экраном, в программе — окно рядом с графом. Одинаковыми они быть не
   обязаны, одинаковым обязан быть файл на выходе.

## 8. Структура папки задачи — контракт ✅ (документ), ⬜ (ноды)

**Контракт живёт отдельным документом: [SRT_EDITOR.md, часть II](./SRT_EDITOR.md).** Он
написан для того, кто настраивает граф обработки: раскладка папки, что обязательно и что нет,
каждое поле документа с типом и последствиями отсутствия, двоичная раскладка пиков,
требования браузера к видео, валидация при открытии и чек-лист приёмки.

Здесь — только решения, из которых он вырос:

```
{sourceRoot}/{имя_исходника}/          ← «задача», её выбирают в меню §6
  dialog.json                          ← документ: дорожки, реплики, переводы, правила
  source.mp4                           ← исходник: кадр + общий звук
  mix.peaks.json                       ← волна общего звука
  01/  orig.srt  es.srt                ← сырьё титров персонажа
  exports/                             ← производное, пересоздаётся редактором целиком
```

1. **`dialog.json` в корне задачи** — источник правды. Формат и правила работы с ним:
   [DIALOG_FORMAT.md](./DIALOG_FORMAT.md).
2. **Папка дорожки — номер.** Имя персонажа живёт в документе, поэтому переименование не
   двигает файлы и не ломает ссылки.
3. **Файлы в папках дорожек — сырьё.** Их не трогает ни редактор, ни экспорт; документ
   ссылается на них через `origin` только чтобы помнить происхождение. Исключение —
   подпапка `{no}/voice/` инструмента озвучки: она внутри папки дорожки, но принадлежит
   не обработке ([TOOLS_VOICEOVER_PLAN.md §4](./TOOLS_VOICEOVER_PLAN.md)).
4. **Минимальная рабочая задача — это `dialog.json` и всё.** Ни видео, ни звука, ни пиков:
   инструмент откроется, покажет реплики и даст их править. Остальное — удобство.
5. **Аудио по персонажам не требуется.** Дорожка в документе — это персонаж со своими
   репликами, а звук нужен один, общий. Появились стемы — заполнят необязательные поля
   дорожки, и редактор покажет свою волну; не появились — ничего не теряется.
6. **Отдельного файла настроек в папке нет.** Правила материала переехали в сам документ
   (`rules`, [DIALOG_FORMAT.md §5](./DIALOG_FORMAT.md)) — одним файлом меньше, и обе
   реализации читают их из одного места.
7. **Пики считает конвейер, не сайт.** У нас нет ffmpeg, а декодировать десятиминутный
   звук в браузере — секунды фриза и сотни мегабайт памяти. Работа делается там, где для
   неё есть инструменты.

**Если раскладка другая.** Задача выбирается человеком, поэтому инструмент не обязан
угадывать: правило чтения `OUT` настраивается у каждого проекта (§9), а если `dialog.json`
в папке нет — предлагается собрать его на месте по шаблону путей из настроек экземпляра.

```jsonc
{
  "sourceRoot": "OUT",
  "trackDir": "{track}",
  "audio": "{track}/audio.wav",
  "origSrt": "{track}/orig.srt",
  "translationSrt": "{track}/{lang}.srt",
  "video": "source.*"
}
```

## 9. Настройки инструмента — свои, в двух местах 🔧

Настройки инструмента **не имеют отношения** к `options.json` проекта и к флагу
`exposedToSite`: то параметры графа обработки, это параметры редактора. С
обработкой инструмент связан ровно двумя вещами — **проектом** (откуда берём
список папок) и **раскладкой внутри `OUT`** (§8).

| Что | Где живёт | Примеры |
|---|---|---|
| дефолты инструмента | реестр в коде (`defaults`, §3) | `sourceRoot: "OUT"`, шаблон раскладки, интервал автосохранения |
| настройки экземпляра | `user_tools.settings` (JSONB) | шаблон раскладки для нестандартных папок, набор языков по умолчанию, автоэкспорт, шаг сетки |
| **правила материала** | **сам документ**, `dialog.json` → `rules` | `maxCps`, `minDurationMs`, `minGapMs`, запрет наложения внутри дорожки |
| состояние интерфейса | `localStorage` браузера | ширина колонок, высоты дорожек, mute / solo / shy, масштаб таймлинии |

**Что из этого уже работает:** `sourceRoot` и `hiddenProjectIds` читаются при
построении выпадающего списка (`source-picker.tsx`), ширина колонки инструментов
запоминается в `localStorage`. Панели настроек экземпляра пока нет — отмечать
проекты, которые не показывать, придётся вместе с ней.

Разделение не косметическое. Правила материала обязаны ехать вместе с папкой и
одинаково действовать в обоих редакторах — поэтому они в документе
([DIALOG_FORMAT.md §5](./DIALOG_FORMAT.md)). Состояние интерфейса, наоборот,
принадлежит одному человеку за одним экраном: в общем файле оно порождало бы
конфликты и запись на каждое движение мыши ([§2.8](./DIALOG_FORMAT.md)).

## 10. Автоматическая синхронизация ⬜

**Новые файлы в папке.** Тот же механизм, что уже крутится в воркспейсе
([workspace-context.tsx:622](../components/account/workspace/workspace-context.tsx#L622)):
`GET /api/storage/v1/tree` → запомнить `cursor` → каждые ~5 с
`GET /api/storage/v1/delta?since=<cursor>`, пока инструмент открыт.

- изменения внутри открытой задачи (новая дорожка, новый язык, обновлённое
  сырьё): нет несохранённых правок — подхватываем молча, тост «Дорожка 03
  добавлена»; есть правки — тост с кнопкой «Обновить», без автозамены;
- `truncated: true` — сбросить локальный индекс и перечитать `tree` (правило из
  [STORAGE_SYNC_CONTRACT.md](./STORAGE_SYNC_CONTRACT.md));
- документ, изменённый другим человеком (или нодой), приезжает тем же дельтой —
  дальше §8 контракта формата.

**Запись документа.** `presign` → PUT → `notify`, условно по ETag (`ifMatch`).
Конфликт `412` разрешается слиянием по `id` реплики — алгоритм не здесь, а в
[DIALOG_FORMAT.md §8](./DIALOG_FORMAT.md): он обязан быть одинаковым в обоих
редакторах, поэтому живёт в контракте формата.

**Автосохранение.** Каждая операция сразу применяется к документу в памяти и
пишется в журнал операций (IndexedDB); документ уходит в R2 раз в ~15 с и при
уходе со страницы. После падения браузера инструмент предлагает восстановить
незаписанное. Журнал — только страховка: файлов он не кэширует и в документ не
попадает.

# Часть III. Модель данных

## 11. Документ `dialog.json` ⬜

Полная схема, правила и алгоритм слияния — [DIALOG_FORMAT.md](./DIALOG_FORMAT.md),
эталонный файл — [dialog.example.json](./dialog.example.json). Здесь только то,
что нужно, чтобы читать остальной план.

- **документ** = медиа + языки + правила материала + дорожки + реплики;
- **дорожка** = персонаж: `id`, номер (`no` = имя папки), имя, цвет, аудио, пики;
- **реплика** = `id`, `trackId`, `startMs`, `endMs`, оригинальный текст, словарь
  переводов, статус вычитки, `rev` для слияния, `origin` (откуда пришла);
- время — **целые миллисекунды**, `endMs` эксклюзивен;
- удалённые реплики помнятся списком `removed` — чтобы повторный прогон ноды не
  воскресил их;
- состояние интерфейса (mute / solo / shy / высоты) в документе **не хранится**.

### Почему свой документ, а не SRT

Ключевой вопрос: как перенести реплику на другую дорожку, если вместе с ней
должны переехать и оригинальный текст, и все переводы.

**Если правда — файлы SRT**, перенос это четыре операции в трёх файлах, и все
должны получиться одновременно: удалить строку из `02/orig.srt`, вставить в
`01/orig.srt`, удалить перевод из `02/es.srt`, вставить в `01/es.srt`. Языков
может быть пять — операций десять. Любая упавшая на середине (закрыли ноутбук,
пропала сеть) оставляет файлы в несогласованном состоянии: реплика есть в
оригинале, а перевод остался на прежней дорожке. Плюс нумерация SRT сквозная,
значит все строки после точки вставки в обоих файлах тоже переписываются.

**Если правда — документ**, реплика это одна запись, а дорожка — её поле:

```jsonc
// было
{ "id": "c_7f3a", "trackId": "t02", "startMs": 26270, "endMs": 29190,
  "text": "So these guys just disappeared.",
  "tr": { "es": { "text": "Así que estos tipos simplemente desaparecieron." } } }

// стало — изменилось ровно одно поле
{ "id": "c_7f3a", "trackId": "t01", "startMs": 26270, "endMs": 29190,
  "text": "So these guys just disappeared.",
  "tr": { "es": { "text": "Así que estos tipos simplemente desaparecieron." } } }
```

Оригинал и все переводы лежат **внутри той же записи**, поэтому копировать
нечего — они уже переехали. Одна операция, одна запись в один файл, нечему
рассинхронизироваться.

**А SRT тогда что?** Проекция, которую мы пересоздаём целиком из документа
(§12). После переноса экспорт дорожки `01` получает эту строку, экспорт `02` её
теряет, нумерация в обоих пересчитывается с нуля. Ручной правки строк в файлах
не существует нигде. Так устроен любой редактор: правда в проекте, рендер
получается из него.

Побочные выгоды того же решения: SRT физически не умеет хранить «эта реплика
проверена», «это перевод той же реплики на трёх языках», «этот персонаж
озвучивается таким голосом» — документ умеет, и инструмент озвучки увидит, что
реплика на дорожке `01` это тот самый `c_7f3a`, а не новая.

## 12. Экспорт ⬜

Экспортёр — чистая функция «документ → набор файлов»; профили и их правила
описаны в [DIALOG_FORMAT.md §7](./DIALOG_FORMAT.md). В v1 инструмент умеет:

| профиль | куда |
|---|---|
| `srt` | `exports/srt/{lang}/{nn}-{name}.srt` |
| `vtt` | `exports/vtt/{lang}/{nn}-{name}.vtt` |
| `json` | сам документ — для передачи в следующий инструмент |

- **Когда:** по кнопке и опционально при каждом сохранении документа (настройка
  `autoExport`, по умолчанию включена — иначе следующий шаг увидит устаревшие
  файлы).
- **Имя файла** — из номера и имени дорожки; переименовал дорожку → следующий
  экспорт лежит под новым именем, а про файлы от прежнего имени инструмент
  говорит вслух и предлагает удалить (молча не удаляет).
- **Сырьё в папках дорожек не перезаписывается никогда.**
- `reaper` — отдельная работа: у Reaper есть и импорт region/marker CSV, и
  формат проекта `.RPP`, и выбирать надо на реальном сценарии озвучки. Граница
  «документ → экспортёр» позволяет добавить профиль потом, не трогая редактор.

# Часть IV. Интерфейс

## 13. Раскладка (зоны со скетча) ⬜


## 15. Превью (зона 2) ⬜

### 15.1. Часы одни

`<video>` — единственный источник времени. Ни таймлиния, ни список, ни звуковые
дорожки своего времени не имеют: они читают `video.currentTime` и рисуют по нему.
Второй источник времени = рассинхрон, который потом невозможно поймать.

**Если видео нет.** По задумке так не бывает — всё начинается с видео, — но файл
может не доехать. Тогда кадр просто не показывается: в зоне превью остаются
**только титры** текущего момента (и подпись, что видео в папке не найдено).
Часы в этом случае берёт `<audio>` общего микса, а при отсутствии и его —
программный таймер на `performance.now()`. Поверхность у всех трёх одна —
`time()`, `play()`, `pause()`, `seek(ms)`, — поэтому остальной код разницы не
видит и таймлиния со списком работают как обычно.

### 15.2. Синхронизация звука

**Обычный случай — звук один** (дорожка видео или `media.mix`), и синхронизировать
нечего: играет сам плеер.

Всё ниже включается только тогда, когда у дорожек **есть** свои аудиофайлы
(необязательное поле `tracks[].audio`). Тогда они играются через WebAudio
(`AudioBufferSourceNode` на дорожку, свой `GainNode`), потому что несколько
`<audio>` расходятся между собой заметнее.

| событие | что делаем |
|---|---|
| `play` | стартуем каждый источник со смещением `video.currentTime`, запоминаем `audioContext.currentTime` начала |
| `pause` | останавливаем источники (WebAudio-источник одноразовый, при следующем `play` создаётся новый) |
| `seek` | останавливаем и стартуем заново с новой позиции |
| каждый кадр (`rAF`) | считаем `drift = (audioContext.currentTime − started) − (video.currentTime − seekedAt)`; при `abs(drift) > 40 мс` — перезапуск источников от текущего времени видео |
| смена скорости | скорость ≠ 1 отключает дорожки персонажей: питч-коррекция тут не нужна, а расхождение неизбежно |

Порог 40 мс выбран как половина типичной длительности слога: меньше человек не
слышит, больше — уже «эхо».

### 15.3. Что звучит

Если у дорожек своего звука нет — звучит общий, и никакой матрицы не нужно.
Матрица ниже применяется только к задачам со стемами; соблюдать её надо целиком,
иначе получается «я нажал solo, а слышу микс»:

| состояние | микс видео | дорожка персонажа |
|---|---|---|
| ни `solo`, ни `mute` | звучит | — |
| есть хотя бы один `solo` | заглушён | звучат только `solo`, у которых есть свой звук |
| есть `mute`, `solo` нигде нет | заглушён | звучат все, кроме выключенных |
| `mute` на всех дорожках | заглушён | тишина |

`solo` старше `mute`: пока `solo` включён хоть где-то, нажатые раньше `M` на
звук не влияют — человек, нажавший `solo`, слышит ровно то, что выбрал, и не
разыскивает забытую кнопку. Оба режима глушат микс: иначе к стему добавляется
тот же голос из микса.

`mute` и `solo` — состояние интерфейса, в документ не пишутся
([DIALOG_FORMAT.md §2.8](./DIALOG_FORMAT.md)).

### 15.4. Титры поверх кадра

Показываются титры **выбранного языка** (переключатель в топбаре, «оригинал» —
тоже вариант) для всех **видимых** дорожек: скрытая через shy дорожка не
рисуется. Если в один момент говорят двое — строки идут друг под другом, с
цветной точкой дорожки. Опционально имя персонажа префиксом. Можно выключить
совсем.

### 15.5. Навигация

- клик по реплике (в списке или на таймлинии) → `seek(startMs)`; кадр показывает
  именно этот момент, воспроизведение не начинается;
- при проигрывании курсор на таймлинии идёт, список автоскроллится, текущая
  реплика подсвечена на всех трёх поверхностях;
- автоскролл **выключается**, как только человек прокрутил список руками, и
  возвращается кнопкой «следовать за курсором» (иначе список выдёргивает из-под
  рук ровно в момент правки);
- покадровый шаг доступен, только если известен `media.fps`; иначе шаг ±100 мс.

## 16. Список реплик (зона 3) ⬜

### 16.1. Модель строки

Строка = реплика. Слева фиксированная колонка **ORIG**, справа по колонке на
язык; кнопки языков над колонками (там же «+ язык», если в `languages.targets`
можно добавить).

| поле | правится | примечание |
|---|---|---|
| номер | нет | порядковый в текущей сортировке, не `id` |
| дорожка | да, выпадающим списком | смена = перенос реплики (`trackId`) |
| `startMs` / `endMs` | да | ввод и как тайм-код `00:00:26,270`, и как секунды |
| длительность | нет | считается; правится через `endMs` |
| текст оригинала | да | `textarea` с автовысотой |
| текст перевода (по колонке) | да | то же |
| подсказки | нет | плотность речи (CPS), отношение длины перевода к оригиналу, длина строк — по `rules` документа |

Подсказки **не блокируют** ввод: подсвечиваются цветом и всё. Блокируются только
физически невозможные вещи — `endMs <= startMs`, длительность меньше
`rules.minDurationMs`, пересечение внутри дорожки при `overlapWithinTrack:
"forbid"`.

Про подсказки важно, какие именно: **CPS здесь не про читаемость, а про плотность речи**
(порог 25, не субтитровые 17 — на реальных сценах 17 срабатывал на 52 репликах из 63 и
превращался в шум). А для дубляжа полезнее другое — **отношение длины перевода к оригиналу**:
реплика обязана уложиться в тот же интервал, и перевод в полтора раза длиннее туда не
втиснуть. Это и есть `maxTranslationRatio` в правилах документа.

И важная оговорка: **правила применяются к правкам, а не задним числом.** Реплика,
пришедшая из обработки короче `minDurationMs`, показывается и правится как обычно
— с предупреждением, без блокировки. В первом же реальном проекте таких нашлось
две («Billy?» на 330 мс, «Yeah.» на 340 мс), и отказ их показывать был бы багом,
а не строгостью.

### 16.2. Виртуализация

Своя, без новых зависимостей: реплик бывают тысячи, а высота строки переменная
(текст в несколько строк).

1. держим массив измеренных высот (по `id`), для неизмеренных — оценка
   `44 px + 18 px × переносы`;
2. рисуем окно `[первый видимый − 15, последний видимый + 15]`;
3. над и под окном — распорки суммарной высоты, чтобы скроллбар был честным;
4. после рендера измеряем фактические высоты (`ResizeObserver`) и, если
   изменились, обновляем распорки **без** скачка позиции: корректируем
   `scrollTop` на разницу высот того, что выше окна;
5. правка текста меняет высоту строки — та же коррекция.

Пункт 4 — то место, где виртуализированные списки обычно дёргаются. Проверять
руками: правка текста в середине списка не должна смещать вид.

### 16.3. Правка и фиксация

- фокус в поле → правка живёт в локальном состоянии строки;
- фиксация в документ: `blur`, `Cmd/Ctrl+Enter`, `Tab`, переход на другую реплику;
- `Enter` — перенос строки внутри текста, **не** фиксация;
- `Esc` — откат правки этого поля;
- одна фиксация = одна операция в undo (§18), а не буква за буквой.

### 16.4. Выделение и групповые действия

`Shift+клик` — диапазон, `Cmd/Ctrl+клик` — добавить/убрать, `Cmd/Ctrl+A` — всё
видимое (с учётом фильтра). Над выделением: перенести на дорожку ▾, сдвинуть
тайминги на ±N мс, пометить «проверено», удалить. Групповое действие = **одна**
операция undo.

### 16.5. Сортировка и фильтры

Сортировка всегда по `startMs` (правило §2.4 контракта) — переключателя нет,
иначе номера строк начинают жить своей жизнью.

Фильтры: по дорожке, по статусу, по тексту (`Cmd/Ctrl+F`) и **«требует
внимания»** — реплики с `status: "conflict"`, с пустым переводом при непустом
оригинале, с нарушением `rules`, и все с дорожки `no: 0`, отсортированные по
`origin.confidence` по возрастанию. Это главный рабочий фильтр: с него человек
начинает.

## 17. Таймлиния (зона 4) ⬜

Самая сложная зона и самая переносимая: она рисуется примитивами на canvas, а
цвета приходят параметром — стиль тут ни при чём (§20).

### 17.1. Система координат

Одна пара функций, через которые проходит **всё**:

```
msToX(ms) = (ms − viewStartMs) × pxPerMs
xToMs(x)  = viewStartMs + x / pxPerMs
```

`pxPerMs` — масштаб, `viewStartMs` — левый край окна просмотра. Оба живут в
состоянии таймлинии, оба сохраняются в `localStorage` по ключу документа.

- масштаб: от «вся длительность в ширину» (fit) до 200 px на секунду; шаг zoom
  ×1.25 за нажатие, `Cmd/Ctrl+колесо` — плавно, курсор мыши остаётся на месте
  (то есть пересчитываем `viewStartMs` так, чтобы `xToMs(mouseX)` не изменился);
- горизонтальный скролл — колесо с `Shift`, drag по линейке, автоскролл при
  проигрывании: курсор дошёл до правого края окна → окно прыгает так, что курсор
  оказывается на трети слева, то есть впереди остаются две трети. Скачком, а не
  плавно: полотно, ползущее под неподвижным курсором, читается хуже — двигается
  всё сразу, и глаз теряет место. Шаг сам собой зависит от масштаба: при мелком
  окно длиннее, и скачков реже;
- перемотка по линейке ведёт полотно за собой: у края окна оно начинает ехать, а
  если курсор мыши вышел за окно — курсор воспроизведения встаёт на самый край и
  полотно уезжает под него. Так до конца материала дотягиваешься одним движением,
  не отпуская кнопку;
- линейка сверху: шаг подписей выбирается из ряда 100 мс / 500 мс / 1 с / 5 с /
  10 с / 30 с / 1 мин — первый, при котором подписи не ближе 60 px.

### 17.2. Слои отрисовки

Один canvas на дорожку, внутри — три слоя в порядке рисования: волна, клипы,
выделение/курсор. Перерисовка целиком по `requestAnimationFrame`, но **только**
если что-то изменилось (флаг `dirty`): React-рендер на кадр не годится, а
постоянная перерисовка греет ноутбук на пустом месте.

Триггеры перерисовки: смена `pxPerMs` / `viewStartMs`, движение курсора при
проигрывании, любое изменение реплик этой дорожки, hover, drag, изменение
высоты дорожки, смена темы.

### 17.3. Волна: своя, если есть, иначе общая

Волна рисуется **на каждой дорожке**, за клипами. Что именно рисуем — решается по
дорожке:

| у дорожки | рисуем |
|---|---|
| заполнено `peaks` (есть свои стемы) | её собственную волну |
| `peaks` пусто (обычный случай) | **общую** волну из `media.peaks` |
| нет ни своих пиков, ни `media.peaks`, но звук есть | считаем в фоне (`OfflineAudioContext`) и держим в памяти страницы |
| звука нет вовсе | полоса пустая: линейка и клипы. Это **не** аварийный режим, тайминги и текст правятся и так |

Так на дорожке всегда есть ориентир: по волне видно, где реально началась речь, а
это главный источник правок таймингов.

**Общую волну надо рисовать тише.** Одна и та же волна на трёх дорожках легко
читается как «это звук именно этого персонажа». Поэтому подставная волна рисуется
приглушённым цветом (та же кривая, меньше контраста), а в шапке дорожки стоит
пометка «общая». Своя волна — полным цветом дорожки. Разница должна быть видна
без наведения мыши.

**Отдельной полосы «Микс» по умолчанию нет** — она показывала бы то же, что и
фон дорожек. Переключатель «показать общую волну отдельной полосой» есть в меню
таймлинии и полезен, когда у части дорожек появились свои стемы: тогда общая
картина звука уже не видна ни на одной дорожке.

**Формат пиков** — пары min/max с шагом `1000/pps` мс. Для колонки пикселей берём
все пары, попадающие в её диапазон, и рисуем вертикальную линию от min до max.
При сильном zoom-in пар на пиксель меньше одной — интерполяции нет, рисуем
ступеньками: честнее, чем гладкая кривая, которой в данных нет.

Считать пики в браузере — фолбэк, а не план: десятиминутный звук это секунды
фриза и сотни мегабайт памяти, и результат не переживёт перезагрузку страницы.
Поэтому пики даёт конвейер (§V.4).

### 17.4. Клипы

Прямоугольник от `msToX(startMs)` до `msToX(endMs)`, внутри — начало текста,
обрезанное по ширине. Минимальная ширина отрисовки 3 px, чтобы короткие реплики
не исчезали. Цвет — из цвета дорожки; статус `approved` — сплошная заливка,
`auto` — штриховка, `conflict` — красная рамка.

**Хит-тест** (порядок важен): ручка правой границы (6 px внутрь) → ручка левой
границы → тело клипа → пустое место дорожки. Ручки не сжимаются на узких клипах:
если клип меньше 18 px, ручек нет вообще, только тело — иначе взять клип
невозможно.

### 17.5. Drag — конечный автомат

```
idle ─(mousedown на теле)→ maybeDrag ─(сдвиг > 3 px)→ dragBody ─(mouseup)→ commit
  │                            └─(mouseup без сдвига)→ select
  ├─(mousedown на ручке)→ dragEdge ─(mouseup)→ commit
  └─(mousedown на пустом)→ rubberBand ─(mouseup)→ selectRange
```

- порог 3 px отделяет клик от перетаскивания (без него любой клик двигает реплику);
- во время drag рисуется **призрак** на новом месте, документ не меняется:
  правка применяется один раз на `mouseup` → одна операция undo;
- `dragBody` по вертикали через границу дорожки = смена `trackId`; подсвечиваем
  дорожку-цель, при недопустимом переносе (пересечение при `forbid`) курсор
  «нельзя» и отмена на отпускании;
- `Esc` во время drag отменяет всё;
- `Alt` отключает прилипание;
- выход курсора за края окна во время drag — автоскролл со скоростью,
  пропорциональной выносу.

### 17.6. Прилипание

Порог **6 px** (в миллисекундах это `6 / pxPerMs`, то есть на разном zoom
разное — так и надо: прилипание должно быть «на глаз»). Кандидаты, в порядке
приоритета: курсор воспроизведения → границы соседних реплик той же дорожки →
границы реплик других дорожек → круглые секунды → границы речи из волны (если
пики есть: край участка, где уровень поднимается выше порога).

Последний кандидат — самый полезный на практике: тайминги от автоматики часто
съезжают на 100–200 мс, и прилипание к фактическому началу речи экономит человеку
основную часть работы.

### 17.7. Запреты

`endMs − startMs >= rules.minDurationMs`; `startMs >= 0`; `endMs <=
media.durationMs` (за границу тянуть нельзя, но существующие реплики за границей
показываем — файл мог прийти с неточной длительностью); пересечение внутри одной
дорожки при `overlapWithinTrack: "forbid"`. Между дорожками пересечения
разрешены всегда.

### 17.8. Панель дорожек слева

| Элемент | Поведение |
|---|---|
| имя | inline-переименование → имя персонажа в документе и имена файлов экспорта (§12) |
| `M` | mute — **только если у дорожки есть своё аудио** (§15.3), иначе кнопки нет |
| `S` | solo — то же условие |
| `👁` | пометить дорожку как shy |
| высота | drag за нижнюю границу, 32–160 px; двойной клик — сброс к 64 px |
| цвет | палитра категорий ([UI_TOKENS.md §2.6](./UI_TOKENS.md)) |
| счётчик | сколько реплик на дорожке |

Сверху панели: поиск по дорожкам (фильтрует список), кнопка **shy** (скрыть или
показать все помеченные — как в After Effects), zoom `−` / `+`, «fit».

Порядок сверху вниз: `no: 0` («не распознано»), если непустая, затем дорожки
персонажей по `no`. Полоса общей волны — необязательная, включается в меню
таймлинии (§17.3).

### 17.9. Объединение дорожек — главная операция на реальных данных

Автоматика чаще всего ошибается не в тексте, а в том, что **один человек
получает несколько дорожек**: в реальном прогоне на «Moneyball» вышло 9 дорожек
на ~7 говорящих, на «The Big Short» — 12 на ~7. Значит объединение дорожек это не
редкая операция из подменю, а то, с чего человек начинает работу.

- перетащить шапку дорожки на другую → «объединить с …?» с подтверждением;
- в контекстном меню дорожки — «объединить с ▾» со списком остальных;
- при объединении: реплики переезжают на дорожку-цель и получают `movedFrom`,
  дорожка-источник исчезает, в документ пишется `mergedTracks`
  ([DIALOG_FORMAT.md §4](./DIALOG_FORMAT.md)) — чтобы следующий прогон ноды не
  создал её заново;
- имя цели сохраняется, у пустой дорожки-источника подтверждения не спрашиваем;
- одна операция undo (§18.1) — откат возвращает и дорожку, и реплики.

Помощь человеку, которая тут стоит дороже красоты: рядом с дорожкой показывать
число реплик и среднюю уверенность, а в меню объединения сортировать кандидатов
по близости средней уверенности и по смежности во времени — раздробленные части
одного человека обычно не пересекаются между собой и идут подряд.

### 17.10. Контекстное меню клипа

Разделить по курсору (`Cmd/Ctrl+K`) — это же лечит mixed-turn, когда автоматика
склеила в одну реплику двух говорящих. Дальше: объединить с соседним справа, дублировать,
удалить, перенести на дорожку ▾, «создать пустую реплику» (доступно и на пустом
месте дорожки — это основной способ перенести текст руками).

Разделение: новая реплика получает новый `id`, `origin.kind: "manual"`, текст
делится по позиции каретки, если правка шла в тексте, иначе весь текст остаётся
в левой части. Перевод при разделении **не** делится автоматически — остаётся
слева, справа пустой: машинально порезанный перевод хуже пустого.

## 18. Операции, undo и автосохранение ⬜

### 18.1. Закрытый список операций

Всё, что делает человек, выражается **одной из** операций ниже. Больше их не
становится: новая функция интерфейса должна раскладываться на существующие, иначе
undo, слияние и автосохранение придётся переделывать втроём.

| операция | параметры | заметки |
|---|---|---|
| `cue.edit` | `id`, поле, было → стало | текст, перевод, `note`, `status` |
| `cue.time` | `id`, `startMs`/`endMs` было → стало | drag границ, ввод тайм-кода |
| `cue.move` | `id`, `trackId` было → стало | ставит `movedFrom` |
| `cue.shift` | `id[]`, `deltaMs` | групповой сдвиг |
| `cue.add` | новая реплика целиком | пустая или разделением |
| `cue.remove` | `id[]` | дописывает `removed` |
| `cue.split` | `id`, `atMs`, позиция каретки | = `cue.time` + `cue.add` одной операцией |
| `cue.merge` | `id`, `idNext` | тексты через пробел, `endMs` от второго |
| `track.rename` | `id`, было → стало | |
| `track.add` / `track.remove` | дорожка | `remove` только у пустой дорожки |
| `track.merge` | `from`, `into` | реплики переезжают (`movedFrom`), дорожка `from` исчезает, в документ пишется `mergedTracks` |
| `track.reorder` | `id`, `no` | |
| `doc.rules` | поле, было → стало | правка `rules` |

Каждая операция обратима по своим «было → стало» — этого достаточно и для undo, и
для журнала восстановления. Отдельного «состояния до» хранить не нужно.

### 18.2. Undo

Стек операций, не DOM-событий и не снимков документа. Глубина 200, сбрасывается
при смене задачи. Одно движение человека = одна операция: drag от `mousedown` до
`mouseup` — одна, правка текста от фокуса до фиксации — одна, групповое действие
над выделением — одна.

`redo` очищается первой новой операцией после undo. Слияние извне (§10) undo не
затрагивает: чужие правки не наши, откатывать их нельзя.

### 18.3. Автосохранение

Операция → применяется к документу в памяти → пишется в журнал (IndexedDB) →
через 15 с бездействия или по `Cmd/Ctrl+S` документ уходит в R2. При уходе со
страницы — попытка синхронной записи журнала (не документа: сеть в `beforeunload`
ненадёжна).

Восстановление: при открытии задачи сверяем `revision` документа с последней
записью журнала. Журнал новее — предлагаем «применить незаписанные правки»
списком, что именно будет применено. Молча применять нельзя: человек мог уйти
именно потому, что напортил.

### 18.4. Горячие клавиши

| Клавиши | Действие |
|---|---|
| `Space` | play / pause |
| `J` `K` `L` | назад / стоп / вперёд, повторное нажатие ускоряет |
| `←` `→` | ±100 мс (`Shift` — ±1 с; при известном `fps` — ±кадр) |
| `↑` `↓` | предыдущая / следующая реплика |
| `[` `]` | поставить `startMs` / `endMs` текущей реплики по курсору |
| `Cmd/Ctrl+K` | разделить реплику по курсору |
| `Cmd/Ctrl+D` | дублировать |
| `Delete` | удалить выделенные |
| `Cmd/Ctrl+Z` · `Cmd/Ctrl+Shift+Z` | undo / redo |
| `Cmd/Ctrl+S` | сохранить (и экспорт, если `autoExport`) |
| `Cmd/Ctrl+F` | поиск по тексту реплик |
| `M` `S` | mute / solo дорожки под курсором |
| `Esc` | отменить drag, откатить правку поля, снять выделение |

Внутри текстового поля работают только `Esc`, `Cmd/Ctrl+Enter`, `Tab` и `Cmd/Ctrl+S`
— остальные буквенные сочетания отдаём вводу.

## 20. Что переносится в программу как есть ⬜

Разделение не «сайт против программы», а **логика против оформления**. Список
ниже — то, ради чего документ доводится до этого уровня подробности.

### 20.1. Переносится строчка в строчку (стиль ни при чём)

| что | почему переносимо |
|---|---|
| работа с документом: разбор, валидация, слияние, детерминированная запись | чистые функции над JSON, контракт один ([DIALOG_FORMAT.md](./DIALOG_FORMAT.md)) |
| закрытый список операций и undo (§18.1–18.2) | структуры данных, ни одного элемента интерфейса |
| экспортёры `srt` / `vtt` (§12) | текст на выходе обязан совпадать до байта |
| координаты и масштаб таймлинии (§17.1) | две функции и два числа |
| отрисовка волны и клипов (§17.2–17.4) | canvas-примитивы; цвета приходят параметром, а не из UI-кита |
| хит-тест и автомат drag (§17.4–17.5) | математика на координатах |
| прилипание (§17.6) и запреты (§17.7) | числа и правила из `rules` |
| математика виртуализации (§16.2) | измерения и распорки, без разметки |
| синхронизация плеера и матрица звука (§15.1–15.3) | WebAudio и `<video>` одинаковы в браузере и в webview |
| сборка реплик из блоков и сопоставление переводов | алгоритм из `DIARIZATION_NODE_PLAN.md` §5 |

### 20.2. Пишется заново под свой UI-кит

Кнопки, панели, поля ввода, модалки, топбар, выпадающие меню, раскладка со
сплиттерами, тема и иконки. На сайте это Tailwind + Radix, в программе MUI +
emotion. Это самая дешёвая часть работы — и та, где одинаковость как раз не нужна:
инструмент должен выглядеть как то приложение, в котором открыт.

### 20.3. Как писать код на сайте, чтобы перенос был возможен

Не «архитектура на будущее», а три правила:

1. **Функции без React отдельно от компонентов.** Всё из §20.1 — в файлы, которые
   не импортируют ни React, ни `cn()`, ни компоненты. Проверка простая: файл, где
   есть `import` из `components/`, переносу не подлежит.
2. **Цвета и размеры — параметром.** Рисующие функции принимают палитру
   (`{ waveform, clip, clipApproved, cursor, … }`), а не читают токены сами.
3. **Состояние отдельно от представления.** Хуки, которые возвращают данные и
   команды, без разметки: `useDialogDoc`, `useTimelineView`, `usePlayerClock`,
   `useSelection`. В программе они переедут почти без правок, а компоненты вокруг
   них будут свои.

## 21. Порядок работы над второй реализацией ⬜

Когда версия на сайте работает:

1. прочитать [DIALOG_FORMAT.md](./DIALOG_FORMAT.md) целиком — это контракт, а не
   рекомендация;
2. перенести файлы из §20.1 как есть, прогнать проверку «открыл
   `dialog.example.json` → сохранил → файл побайтово тот же»;
3. собрать вокруг них своё представление (§20.2), сверяясь с §13–§18: там описано
   поведение, а не внешний вид, и расхождение в поведении — баг, а не вкусовщина;
4. заменить доступ к файлам: вместо `presign` / PUT / `notify` — файловые команды
   программы, вместо поллинга `delta` — вотчер, вместо `ifMatch` — сверка
   `mtime` + `size` (алгоритм слияния тот же, [DIALOG_FORMAT.md §8](./DIALOG_FORMAT.md));
5. прогнать один и тот же материал в обеих реализациях и сравнить экспорт: файлы
   должны совпасть.

Что считать «готово»: обе реализации на одном документе дают одинаковый экспорт и
одинаково ведут себя на списке из §13–§18. Внешний вид при этом разный — это норма.

## V.3. Разделение по персонажам — спроектировано отдельно ⬜

Диаризации не делает ни одна нода: `transcribeVA` (whisper) её не умеет, а `AItranslateVA`
передаёт `num_speakers` во внешний сервис дубляжа и забирает **один смикшированный** результат.
Без разделения оба редактора остаются редакторами одной дорожки.

Цепочка нод, формат промежуточного файла, настройки и выбор движка вынесены в отдельный план на
стороне программы: **`fs.manager.tauri/ideasAndTest/DIARIZATION_NODE_PLAN.md`**. Коротко, что
оттуда важно знать сайту:

| решение | следствие для сайта |
|---|---|
| распознавание — **один** проход по целому файлу, диаризация отдельно, слова получают спикера по перекрытию | реплики документа собираются из слов, а не из готовых SRT: тайминги точнее, текст лучше |
| нумерация спикеров — **по первому появлению**, номера не переиспользуются | номер дорожки остаётся идентификатором, на который можно ссылаться (`movedFrom`, документы следующего шага) |
| текст, которому спикера не нашлось, кладётся на дорожку **`no: 0` «не распознано»** | редактор показывает её первой; перенос реплик с неё на персонажей — основная работа человека. В экспорт дорожка не идёт |
| у реплики пишется `origin.confidence` | фильтр «требует внимания» сортирует по нему: сначала сомнительное |
| стемы дорожек — **той же длительности**, что исходник (тишина вместо чужой речи, паузы не вырезаются) | тайминги документа, волна и видео совпадают всегда |

Ноды цепочки: `diarizeSpeakers` → `dialogDocBuild` (§V.5, режим «слова + диаризация») →
`splitBySpeaker` → `audioPeaks` (§V.4).

**Что не блокируется этим пробелом.** Редактор умеет создавать дорожки и переносить в них
реплики, поэтому M1–M3 разрабатываются и проверяются на документе, собранном руками, ещё до
появления диаризации.

## V.4. Новая нода `audioPeaks` ⬜ — пики для таймлинии

Самая простая часть: почти дубликат `speech2signal`, только вывод другой.

```jsonc
// plugins-dev/audioPeaks/plugin.json
{
  "id": "audioPeaks", "name": "Audio Peaks", "version": "0.1", "apiVersion": 1,
  "type": ["nodeui", "processing"],
  "description": "Пики громкости аудио в JSON для отрисовки волны на таймлинии.",
  "main": "audioPeaks.js", "ui": "ui.json", "external": [],
  "cost": "0", "costUnit": "run", "resourcePool": "ffmpeg"
}
```

- **Вход:** `_item.import.inputFile` — один или несколько аудиофайлов.
- **Свойства (`ui.json`):** `pps` (пиков в секунду, slider 20–200, по умолчанию
  50), `bits` (8 / 16, по умолчанию 8), `targetPath` (маска пути).
- **Как считает:** тот же вызов, что в `speech2signal` —
  `ffmpeg -af asetnsamples=n=…,astats=metadata=1:reset=1,ametadata=print:file=-`,
  затем `parseAstatsEnvelope`. Из огибающей (`rms[]`, `hopMs`) собираются пары
  min/max на пиксель. Ничего нового изобретать не нужно, функция уже есть и
  протестирована двумя нодами.
- **Выход:** `<имя аудио>.peaks.json` рядом с аудио (или по маске):

```jsonc
{ "version": 1, "pps": 50, "bits": 8, "dur": 718.4, "data": "<base64 int8 пар min/max>" }
```

- Возвращает путь созданного файла — дальше он попадёт в `dialogDocBuild`.

## V.5. Новая нода `dialogDocBuild` ⬜ — собирает документ задачи

Нода-финализатор: складывает то, что насчитали предыдущие ноды, в раскладку §8 и
пишет `dialog.json`. Без неё редактор вынужден угадывать структуру по именам
файлов, а имя персонажа взять негде — папка дорожки это номер.

```jsonc
// plugins-dev/dialogDocBuild/plugin.json
{
  "id": "dialogDocBuild", "name": "Dialog Doc Build", "version": "0.1",
  "apiVersion": 1, "type": ["nodeui", "processing"],
  "description": "Собирает папку задачи и документ dialog.json для редактора реплик.",
  "main": "dialogDocBuild.js", "ui": "ui.json", "external": [],
  "cost": "0", "costUnit": "run", "resourcePool": "helpers"
}
```

- **Вход, два режима:**
  1. **слова + диаризация** (основной, §V.3): `words.json` от `transcribeVA` в формате
     `jsonfull` плюс `diarization.json` — реплики собираются из слов, спикер определяется по
     перекрытию. Алгоритм и пороги — `DIARIZATION_NODE_PLAN.md` §5;
  2. **готовые SRT** (простой): исходник, аудио дорожек, SRT оригиналов и переводов — разбор по
     расширению и по свойствам ноды.
- **Свойства (`ui.json`):**

| id | контрол | смысл |
|---|---|---|
| `taskPath` | autocomplete (маска) | куда складывать задачу, например `$localFolder/OUT/$clearName` |
| `speakerNames` | textedit | имена персонажей по порядку дорожек через запятую; пусто → `Speaker 1`, `Speaker 2` |
| `langFromName` | checkbox | брать код языка из суффикса имени файла (`_es`, `.es`) |
| `origSuffix` | textedit | как узнать оригинальный SRT (по умолчанию `orig`) |
| `moveFiles` | checkbox | переносить файлы или копировать |
| `rules` | textedit | правила материала для документа: `maxCps`, `minDurationMs`, `minGapMs` |

- **Что делает:**
  1. создаёт папку задачи и подпапки дорожек по номерам;
  2. раскладывает файлы (`fs.copy` / `fs.move`);
  3. определяет язык каждого SRT (суффикс имени или порядок);
  4. собирает `dialog.json` по [DIALOG_FORMAT.md](../docs/DIALOG_FORMAT.md):
     реплики из `orig.srt`, переводы сопоставляются по индексу, при расхождении
     числа реплик — по перекрытию таймингов; `origin` заполняется у всех;
  5. **если документ уже существует — только дописывает** новые дорожки и новые
     реплики, существующие не трогает, удалённые из `removed` не воскрешает
     ([DIALOG_FORMAT.md §9](../docs/DIALOG_FORMAT.md));
  6. `exports/` не трогает никогда.
- **Выход:** путь к `dialog.json` (плюс список созданных файлов).

Важное следствие правила 5: нода — не владелец документа, а его первый автор.
Прогон обработки может случиться после того, как человек уже поправил реплики;
перезапись уничтожила бы работу, отказ от дописывания оставил бы новые дорожки
невидимыми.

## V.6. Что нужно от программы, кроме двух нод ⬜ — ничего

Инструмент на сайте работает только с онлайн-папкой (§7), поэтому окон,
capability, локальных мостов и прокидывания событий файловой системы **на стороне
программы не требуется**. Всё, что нужно: две ноды выше, чтобы папка `OUT`
приезжала с документом и пиками.

## V.7. Локальный редактор — отдельная работа в программе ⬜

Живёт в `fs.manager.tauri`, план — `ideasAndTest/DIALOG_EDITOR_PLAN.md`. Общий с
сайтом только формат документа ([DIALOG_FORMAT.md](./DIALOG_FORMAT.md)); код UI
не переносится ни в одну сторону.

Разрез там такой: **окно и React — в ядре, логика документа — в системном
плагине** (`type: ["system"]`, как `updater` и `remoteWorker`; такой плагин
загружается из любого окна и получает файловый доступ через `hostServices`).
Плагин не может принести свой интерфейс — UI плагина это `ui.json`, то есть нода
в графе, а contribution points отложены осознанно. Подробнее — в самом плане §2.

Для сайта отсюда важно одно: бандл того плагина здесь не пригодится (ни
`plugin://`, ни `hostServices` у нас нет), а вот **исходник чистой логики** —
разбор, валидация, слияние, экспортёры — стоит держать одной копией на два
репозитория и копировать скриптом со сверкой. См. открытый вопрос №2.

## V.8. Реальный конвейер: Cast Analyzer Next ✅ (данные есть)

Разделение по персонажам уже сделано — не нами и не в графе: отдельная программа
**Cast Analyzer Next** (0.21.0-alpha.21). Её выход разобран, формат на него
ложится, конвертер написан:

```bash
node scripts/import-castanalyzer.mjs --project <DUB/Movie> \
     --video <file.mp4> --out <dir> [--stems]
```

Это прототип ноды `dialogDocBuild` (§V.5) — та же работа снаружи конвейера, чтобы
получить настоящие данные для редактора уже сейчас.

### Что она отдаёт и куда это кладётся

| Cast Analyzer | наш документ |
|---|---|
| `04_SUBTITLES/all_dialogue.json` — 63 реплики: `start`/`end` (сек), `text`, `speaker_name`, `confidence`, `needs_review`, `reason` | `cues[]`: миллисекунды, `text`, `trackId`, `origin.confidence`, `origin.needsReview`, `origin.reviewReason` |
| `04_SUBTITLES/SPEAKER_XX.srt`, `UNKNOWN.srt` | сырьё титров в `NN/orig.srt` (`UNKNOWN` → дорожка `no: 0`) |
| `03_CAST/cast.json` — имена, число реплик, секунды речи, `face_status` | `tracks[].name`, статистика в шапке дорожки |
| `02_ANALYSIS/analysis.json` — `pipeline`, `app_version` | `tracks[].diar.engine` |
| `05_AUDIO_STEMS/SPEAKER_XX_guide.mp3` — полная длительность фильма, тишина вне своих реплик | `tracks[].audio` (только с `--stems`) |
| `05_AUDIO_STEMS/SPEAKER_XX/clips/0001_000000110-000002320.mp3` — нарезка по репликам | пока не используем; это материал для инструмента озвучки |

Приятная деталь: правило стемов у них сформулировано так же, как у нас
независимо — «full movie timeline; silence outside assigned turns». Тайминги
остаются общим языком всей цепочки.

Переводов на этом шаге нет: `languages.targets` пустой, колонок перевода в
редакторе не будет, пока их не добавит следующий шаг конвейера. Инструмент обязан
корректно работать с нулём языков.

### Что её benchmark говорит про наш интерфейс

Замеры по восьми сценам: ~92.7 % с требованием «один человек = один Character
ID», ~95.4 % если разрешить одному человеку быть раздробленным на несколько
дорожек, и ~87 % на новых материалах. Полезнее среднего — **как именно** она
ошибается, потому что каждая ошибка это операция, которую человек делает руками:

| ошибка автоматики | как часто | чем лечится в редакторе |
|---|---|---|
| один человек раздроблен на несколько дорожек | Moneyball: 9 дорожек на ~7 говорящих; Big Short: 12 на ~7 | **объединение дорожек** (§17.9) — главная операция, а не пункт из подменю |
| двое склеены в одну дорожку | 12 Angry Men | новая дорожка + перенос реплик (§16.4, §17.5) |
| реплика без персонажа (`UNKNOWN`) | 6–7 на сцену | дорожка `no: 0`, разнести по персонажам |
| mixed-turn: в одной реплике двое | Iron Man 2, отдельно отмечено как нерешённое | разделение реплики по курсору (§17.10) |
| помечено «нужна проверка» | 24 из 63 реплик в Moneyball | фильтр «требует внимания» по `needsReview` и `confidence` (§16.5) |

Отсюда два вывода для интерфейса. Первый: дорожек бывает **до 12**, и поиск по
дорожкам, shy и регулировка высоты — не украшения, а условие работы. Второй:
инструмент должен быть быстрым именно на этих пяти операциях; всё остальное можно
делать медленно.

# Часть VI. Этапы

| Этап | Объём |
|---|---|
| **M1** | Вкладка «Инструменты», модалка каталога, `user_tools` + API, каскадное меню источника, чтение `dialog.json`, список реплик и превью — только просмотр |
| **M2** | Правка текста и таймингов, запись документа с `ifMatch` и слиянием, автосохранение и восстановление, экспорт `srt` / `vtt`, подхват новых файлов через `delta` |
| **M3** | Таймлиния: дорожки, волна из пиков, клипы, drag границ и клипов, перенос между дорожками, пустая реплика, mute / solo / shy / поиск / zoom |
| **M4** | Undo/redo, горячие клавиши, CPS и валидации по `rules`, фильтр «требует внимания», фолбэк-расчёт пиков, сборка документа для папки без `dialog.json` |
| **M5** | Профиль экспорта `reaper` (после разбора формата) и то, что попросит первый живой прогон |

Данные для M1 есть, и настоящие: `scripts/import-castanalyzer.mjs` собирает папку
задачи из проекта Cast Analyzer (§V.8) — восемь разобранных сцен, до 12 дорожек,
`UNKNOWN`, реплики на проверку. Рядом `scripts/make-dialog-fixture.mjs` даёт
синтетический комплект под неудобные случаи, которых в реальных данных пока нет:
переводы, `conflict`, незнакомое поле, перекрытие дорожек, отсутствие медиа.

Ноды `audioPeaks` и `dialogDocBuild` (§V.4–V.5) нужны, чтобы это работало внутри
конвейера, а не скриптом руками — но разработку интерфейса они не задерживают. Локальный редактор в программе (§V.7) идёт своим
графиком и на этапы сайта не влияет.

Каждый этап заканчивается работающим состоянием: M1 — «можно смотреть», M2 —
«можно работать, результат лежит в папке», дальше — скорость и удобство.

# Часть VII. Вне объёма v1

- Озвучка титров и её редактирование — следующий инструмент, отдельное ТЗ.
- Перевод через API (провайдер, ключи, оплата) — перевод приходит от обработки.
- Совместное редактирование в реальном времени: защита от затирания есть
  (`ifMatch` + слияние), присутствия и курсоров других людей — нет.
- Рендер видео с вшитыми титрами.
- Мобильная версия.
- Любая локальная работа с файлами: это отдельный редактор в программе (§V.7).
- Редактор графа обработки на сайте — закрыто в
  [PROJECT_OPTIONS_PANEL.md §1](./PROJECT_OPTIONS_PANEL.md).
