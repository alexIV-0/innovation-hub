## Как поделены обязанности

Зафиксировано, чтобы не возвращаться к вопросу «кто везёт байты».

| | Бэкенд | Клиент |
|---|---|---|
| Каталог (`project_files`) и журнал (`storage_changes`) | владеет | читает через `/tree` и `/delta` |
| Ключи R2 и подписи | выдаёт | считает `s3Key` непрозрачным |
| Байты | не проходят через API | везёт сам, прямо в R2 по presigned URL |
| Права | проверяет | показывает `403` как «нет прав» |
| Локальные копии, что скачано на машине | не знает и не должен | владеет целиком |
| Имена и структура папок | источник истины (Postgres) | строит локальный путь из `folder_path` + `name` |

**Права десктоп-клиента** (решено 2026-08-11): machine token — полный доступ в папке своего
владельца, программа создаёт, переименовывает и удаляет проекты и файлы наравне с сайтом.
Расшаренности она не видит и всегда работает с оригиналом.

## 0. Что клиент гарантирует со своей стороны

Чтобы было понятно, на что можно опираться:

| | Гарантия |
|---|---|
| 1 | После каждого успешного PUT зовём `POST /notify`. Без него мы считаем заливку несостоявшейся |
| 2 | При **перезаливке известного файла передаём его существующий `s3Key`** в `/presign` — чтобы объект перезаписался на месте, а `writeNotifyUpload` (`lib/storage/write-path.ts:232`) нашёл строку по `s3_key` и обновил её, сохранив `file_id` |
| 3 | Присылаем `contentHash` (sha256) и `originMtime` в `/notify` |
| 4 | `/delta` дёргаем один раз на проект за проход обработки, курсор храним на проект, `truncated` обрабатываем полным `/tree` |
| 5 | Логический путь строим из `folder_path` + `name`. `s3Key` считаем непрозрачным и никогда из него путей не выводим |
| 6 | Ключей R2 не имеем и не просим: работаем только через machine token |
| 7 | **Удаление в облако автоматически не отправляем никогда.** Файл, стёртый в зеркале через проводник, просто снова становится «только онлайн»; вотчер удаления игнорирует. Команда `DELETE /object` уходит только от явного действия человека в программе |
| 8 | Каждая машина пишет **свой** файл статистики (`options/__stat/<год>.<месяц>.<machineId>.jsonl`) — две машины не затирают общий объект, конфликтов нет по построению |

## 1. `GET /projects` не отдаёт `userId` — ломает структуру папок у клиента

**Одна строка кода, самый заметный эффект из всего списка.**

`serializeProject` (`app/api/storage/v1/projects/route.ts:57`) собирает ответ без `userId`, хотя
объект проекта его содержит — рядом, в ветке scoped-токена, вы им же проверяете доступ
(`project.userId !== auth.userId`, `:32`).

**Почему для нас это критично.** Раскладка бакета — `projects/{userId}/{projectId}/{folderPath}/…`,
и у нас интерфейс повторяет её тремя колонками:

| Колонка | Что показывает | Откуда имя |
|---|---|---|
| 1 | **пользователь** | ← этого поля и не хватает |
| 2 | проекты пользователя | `projects.name` |
| 3 | содержимое проекта | `project_files.name` |

Без `userId` группировать не по чему: `clients`/`client_id` в живых данных не заполнены ни у одного
проекта, поэтому все проекты (у ADMIN-токена — проекты **всех** пользователей) сваливаются в одну
папку. Вместо структуры получается плоская свалка.

**Что просим:**

```ts
function serializeProject(project) {
  return {
    id: project.id,
    name: project.name,
    clientId: project.clientId,
    userId: project.userId,        // ← добавить
    groupName: project.groupName,
    isActive: project.isActive,
    isPaused: project.isPaused,
    updatedAt: project.updatedAt.toISOString(),
  }
}
```

**И рядом — владельцы с email.** Это не украшение: папка первого уровня должна называться
**email'ом пользователя**, иначе человек не понимает, чья она. Всё нужное в БД уже есть —
`users.email` и `users.full_name` (`lib/repositories/users.ts`, `PUBLIC_USER_FIELDS`), и функция
`listUsers` тоже.

```json
{
  "users":    [{ "id": "093025a9-…", "email": "anya@studio.example", "fullName": "Аня Смирнова" }],
  "clients":  [ … ],
  "projects": [ … ]
}
```

Под ADMIN-токеном — все, кто владеет отданными проектами; под обычным — сам пользователь. Клиент
подписывает папку так: `email` → `fullName` → `displayName` → «Пользователь 093025a9» (первый сегмент
id). То есть пока `users` нет, в первой колонке у человека стоит `Пользователь 093025a9` вместо
`anya@studio.example`.

Если отдавать email нежелательно (персональные данные в ответе на machine token) — скажите, возьмём
`fullName`; но что-то одно нужно, иначе папки остаются подписаны обрезанными UUID.

**Как ведём себя до фикса.** Уровень пользователя уже сделан, а владельца клиент временно добывает
из ключа: сначала из уже загруженного дерева (бесплатно), а если ключей там нет — **из ответа
`POST /presign` на PUT**. Ключ вы строите сами из владельца
(`projectUploadObjectKey(access.ownerId, …)`), и этого достаточно; объект при этом не создаётся —
подпись это только подпись, файл появляется от PUT, строка в каталоге от `/notify`, ни того ни
другого мы не делаем. В логах это будет видно как запросы подписи с именем `owner-probe.tmp` —
файла с таким именем не появится нигде.

Так что обходной путь рабочий, и просьба не про «нам никак», а про три вещи:

- **лишний запрос на проект** при подключении там, где хватило бы поля, которое у вас уже есть;
- **имена**: без `users` папка подписана идентификатором (`Пользователь 093025a9`), а человек ждёт
  своего имени;
- **связанность**: мы читаем ваш формат ключа. Поменяете раскладку — у нас поедет первая колонка.
  Именно поэтому в остальном мы `s3Key` считаем непрозрачным, и это единственное исключение.

`userId` из ответа имеет приоритет, так что после вашей правки обходной путь перестанет вызываться
сам, без изменений у нас.

## 2. Переименование не попадает в журнал — БЛОКЕР для второй машины

`writeRename` (`lib/storage/write-path.ts:443`) журналит изменения только внутри
`if (oldKey !== newKey)` (`:509`), а `oldKey`/`newKey` берутся из `s3_key` (`:494`), который при
переименовании не меняется.

**Две дыры, обе одинаково тихие:**

**2.1. Переименование файла не даёт ни одного события.** У файла с непустым `s3_key`
`oldKey === newKey`, значит блок журнала пропускается целиком: `storage_changes` не пополняется,
`last_seq` у строки не двигается. `GET /delta` о переименовании не расскажет никогда.

**2.2. Переименование папки не журналит её содержимое.** `folder_path` потомков обновляется одним
`UPDATE` (`:472`), но событие пишется только на саму папку. Клиент, который живёт на дельтах, оставит
всех потомков по старому пути.

**Почему это важно именно для нас:** локальный индекс — копия каталога, и он догоняется дельтами.
После переименования на сайте (или на другой машине) мы продолжаем считать, что файл лежит по
прежнему пути. Для нас это не косметика: по логическому пути строится путь на диске, то есть файл
«исчезает» из проекта, а обработка получает путь к несуществующему файлу.

**Что предлагаем.** Два варианта, любой подходит:

- **Проще:** журналить `op: "put"` для переименованной строки **всегда**, независимо от совпадения
  ключей (payload с новыми `name`/`folderPath`), а для папки — плюс `put` на каждого потомка. Ровно
  так уже сделано в `writeFileDelete` (`:312`): там каскад по детям журналится корректно, есть с чем
  сверяться.
- **Дешевле по объёму журнала:** ввести `op: "rename"` с payload `{ fileId, from: {name, folderPath}, to: {name, folderPath}, isFolder }`. Тогда переименование папки — одно событие, а клиенты
  перепишут префикс у себя сами (мы это умеем: `file_id` стабилен, перекачивать ничего не нужно).
  Если выберете этот путь — скажите, добавим обработку `rename` у себя.

**Как ведём себя до фикса:** свои собственные переименования применяем в локальный индекс сами (мы
знаем, что сделали, и ответ `/rename` содержит обновлённую строку). Чужие увидим только после полного
`/tree`. То есть одиночная машина работает, а вот «сайт переименовал → машина увидела» не работает.

## 3. `/reindex` удаляет из каталога строки файлов под `options/`

В `reindexProject` (`lib/storage/write-path.ts:634`) объекты с `/options/` в ключе намеренно не
попадают в `remoteKeys` (`:660`). Но финальный проход (`:741`) удаляет **все** строки
`project_files`, ключей которых нет в `remoteKeys` — вместе с журнальным `op: "delete"`.

**Что это значит:** любой файл под `options/`, у которого есть строка в `project_files`, при первом
же `/reindex` будет объявлен удалённым и удалён из каталога, хотя объект в R2 останется на месте.

Строки под `options/` появляются, когда файл заливается обычным путём `/presign` → PUT → `/notify`
(`writeNotifyUpload` строку создаёт). Сайдкары через `/sidecars` строк не создают, поэтому им ничего
не грозит — проблема ровно у того, что приходит от нас.

**Нас это касается напрямую:** статистика обработки лежит рядом с проектом — `options/__stat/<год>.<месяц>.jsonl`
плюс агрегаты. Это данные о проделанной работе, и терять их из каталога нельзя.

**Что предлагаем** (любое из двух):
- либо не исключать `options/` из листинга в `remoteKeys`, а исключать `options`-строки из прохода
  удаления;
- либо оставить листинг как есть, но в проходе удаления пропускать строки, чей `s3_key` попадает под
  `isOptionsKey` (функция уже есть — `lib/storage/keys.ts:47`).

Второе — одна строка условия, и оно же защищает от повторения этой ошибки в других местах.

## 4. `/reindex` записывает в `name` физическое имя вместе с uuid

Там же: `const name = key.slice(key.lastIndexOf("/") + 1)` (`:688`). Раскладка ключей —
`{folderPath}/{uuid}-{safeName}`, значит для всего, что подобрано реиндексом, логическое имя в
каталоге станет `a3f9c1e2-...-clip.mov`.

Асимметрия: `/notify` пишет **логическое** имя (клиент присылает `fileName`), а `/reindex` —
**физическое**. То есть один и тот же файл называется по-разному в зависимости от того, каким путём
попал в каталог, и это имя видят и сайт, и мы (у нас из него строится имя файла на диске).

**Что предлагаем:** срезать uuid-префикс при реиндексе (он фиксированной формы: `{uuid}-`), либо, если
исходное имя восстановить нельзя, хотя бы не считать реиндекс источником имён для строк, которые уже
есть в каталоге.

Пункт не блокирующий, пока реиндекс не запускают. Но именно реиндекс зовут, когда «что-то
разошлось», — то есть он сработает в самый неудачный момент.

## 5. Проект: создание, переименование, удаление под machine token

`POST /storage/v1/rename` работает со строками `project_files` — то есть с файлами и папками
**внутри** проекта. Мы это уже используем: переименование файла и папки в зеркале идёт через него,
и всё правильно — `s3Key` не трогается, байты не двигаются.

А вот имя самого проекта живёт в `projects.name`, и менять его нечем: `PATCH /api/projects/[id]`
авторизуется через `requireUserApi` (только сессия), machine token туда не пустят.

**Почему это заметно.** В программе колонка проектов выглядит одинаково для локальных и облачных
папок, и человек ожидает, что переименование работает так же. Сейчас пункт меню у онлайн-проекта
приходится показывать серым («Переименовать — на сайте»), а двойной клик по имени не открывает поле
ввода. Это честно, но выглядит как недоделка, и главное — **локальное переименование папки проекта
ломает связь с каталогом**: путь перестаёт разбираться, значки синхронизации исчезают, а в облаке
проект остаётся под прежним именем. Мы это теперь блокируем, но лучше бы просто умели.

> ### ⚠️ Проверено на живом `ffworks.pro` 2026-08-12
>
> `GET /api/storage/v1/projects` под machine token отдаёт по проекту ровно это:
>
> ```
> clientId, groupName, id, isActive, isPaused, name, updatedAt
> ```
>
> То есть **`userId` нет, `isArchived` нет, массива `users` нет** — правки, которые уже лежат в
> рабочем дереве репозитория, на прод не задеплоены. Со стороны программы это выглядит так: архив не
> показывается вообще (нечего показать), а папки владельцев подписаны `Пользователь 093025a9`.
>
> `isPaused` при этом **есть и работает** — «второй проект» приехал с `true`, и галочка в программе
> снимается. Так что направление «сайт → программа» для активности уже живое.

**Как должно быть.** Пользователя (владельца) программа не создаёт — это дело сайта, и мы на это не
претендуем. А вот **проект в папке владельца программа обязана создавать, переименовывать и удалять**:
для человека это такая же обычная папка, как локальная, и «сходи на сайт, чтобы создать проект»
ломает всю работу.

**Что мешает.** `POST /api/projects` и `DELETE /api/projects/[id]` авторизуются через
`requireUserApi` — только сессия. Под machine token их нет, поэтому в программе эти пункты пока
серые. Логика у вас написана, нужен доступ.

**Что просим** — три тонких роута по образцу `rename`, все со `requireStorageApi`:

```http
POST   /api/storage/v1/projects            { "name": "Новый проект", "clientId": null }
→ { "project": { id, name, userId, … } }

POST   /api/storage/v1/project-rename      { "projectId": "…", "name": "Новое имя" }
→ { "project": { … } }

DELETE /api/storage/v1/projects            { "projectId": "…" }
→ { "ok": true }   // вместе с содержимым — в корзину, см. пункт 6
```

Внутри — то, что уже написано (`UPDATE projects SET name`, существующие create/delete из кабинета),
плюс `requireOwnedProjectAccess` на изменяющих. Ключи в бакете от имени проекта не зависят, так что
переименование это одна строка SQL и ноль операций в R2. Журналить имя не обязательно: в
`storage_changes` оно не участвует, мы перечитаем его следующим `/projects`.

### 5.1. Включить/выключить проект под machine token

**Новых полей в БД не нужно** — колонка `is_paused` уже есть, её пишет сайт, и она приезжает в
`/projects`. Не хватает только эндпоинта, чтобы флаг мог поставить и клиент:

```http
POST /api/storage/v1/project-state
{ "projectId": "…", "paused": true }
→ { "project": { … } }
```

`requireStorageApi` + `requireOwnedProjectAccess`, внутри — `UPDATE projects SET is_paused`.

**Почему это нужно.** Галочка «проект активен» во второй колонке программы и переключатель на сайте —
одно и то же состояние. Сейчас оно ездит только в одну сторону: выключил на сайте → в программе
галочка снялась; выключил в программе → сайт не узнал, а следующий `/projects` вернул галочку обратно.
Для человека это выглядит как «переключатель не работает».

Клиент уже написан под этот роут (как и под `project-rename`) — появится эндпоинт, заработает без
наших правок.

**Про `folderState.json`:** мы обсуждали и второй путь — держать активность в сайдкаре
`options/folderState.json`, который живёт в зеркале и заливается как обычный файл. Он рабочий, но
тогда на один флаг получается **два источника истины** (сайдкар и `projects.is_paused`), а сайт пишет
именно колонку. Поэтому предлагаем колонку считать истиной для облачных проектов, а сайдкар оставить
локальным папкам и офлайн-кэшу. Если решите наоборот — скажите, у нас это разница в одну ветку.

---

Приоритет внутри пункта: **создание и переименование** нужны в первую очередь — это ежедневные
действия (человек заводит проект прямо в работе и тут же его переименовывает). Удаление — следом, и
оно должно уходить в корзину (пункт 6), а не стирать данные насовсем.

### 5.2. `is_active` — зеркало без гарантии

В `STORAGE_API.md` написано, что `isActive` — legacy-зеркало `!isPaused`, и на живых данных так и есть:
у «второй проект» пришло `isActive=false, isPaused=true`, у остальных пяти — наоборот. Зеркало
соблюдается.

**Но соблюдается оно вручную.** Это две независимые колонки: `is_active` добавлена отдельной миграцией
(`db/migrations/2026-07-31-account-workspace-columns.sql`, `DEFAULT TRUE`), и обновляются они одним
`UPDATE`, но каждая своим параметром:

```sql
is_paused = COALESCE($6, is_paused),
is_active = COALESCE($7, is_active),
```

Ничто на уровне схемы не заставляет их совпадать. Достаточно одного места, где обновили одну и забыли
другую, — и получится «на сайте проект активен, в программе выключен» без видимой причины. Отладка
такого стоит дорого именно потому, что оба значения выглядят правдоподобно. Плюс у `is_active` есть
независимый потребитель: выборка чатов Yougile фильтрует `WHERE is_active = TRUE`
(`lib/repositories/projects.ts:383`).

**Что предлагаем** — одно из двух, оба дешёвые:

1. **Убрать `is_active`** в пользу `is_paused`, а Yougile-выборку переписать на `WHERE is_paused = FALSE`.
   Одно состояние — одна колонка, расходиться нечему.
2. Если колонка нужна для совместимости — **закрепить инвариант в БД**, чтобы он не зависел от
   аккуратности вызывающего:

```sql
ALTER TABLE projects DROP COLUMN is_active;
ALTER TABLE projects ADD COLUMN is_active BOOLEAN
  GENERATED ALWAYS AS (NOT is_paused) STORED;
```

**Со стороны клиента это не блокер:** мы читаем `is_active`, но **ни одного решения на ней не
принимаем** — галочка активности и пропуск обработки висят на `is_paused` и `is_archived`. Так что
менять можно свободно, у нас ничего не отвалится.

## 6. Корзина удалённых объектов (30 дней) — ЗАЩИТА ОТ ПОТЕРИ ДАННЫХ

`writeFileDelete` (`lib/storage/write-path.ts:312`) удаляет **насовсем и сразу**: строка уходит
`DELETE FROM project_files`, объект — `DeleteObjectCommand` в R2 (`:434`). Отменить нельзя ничем.

**Почему это для нас критично.** В программе удаление сделано двухступенчатым осознанно:

1. первое нажатие — стирается только **локальная копия**, файл остаётся в облаке со значком
   «только онлайн»;
2. второе нажатие (файл уже только в облаке) — команда `DELETE /object`.

Смысл второй ступени в том, что она не должна быть точкой невозврата. Сейчас же второе нажатие
уничтожает мастер безвозвратно, и единственная защита — что человек нажмёт не два раза. Для видео,
которое считали часами, это неприемлемо.

**Что просим:**

- `DELETE /storage/v1/object` — **мягкое** удаление: строка помечается удалённой (`deleted_at`), объект
  в R2 **остаётся**; в журнал по-прежнему `op: "delete"` (клиенты убирают его из списков — у нас это
  уже работает);
- **ретеншен 30 дней**: фоновая задача (или lifecycle-правило бакета по префиксу корзины) стирает
  объект и строку окончательно;
- по возможности — два роута для корзины:

```http
GET  /api/storage/v1/trash?projectId=…      → { items: [{ fileId, name, folderPath, deletedAt }] }
POST /api/storage/v1/trash/restore          { "fileId": "…" }  → { file: { … } }
```

Восстановление нам нужно не срочно: главное — чтобы **байты не пропадали сразу**. Список корзины и
кнопку «восстановить» мы добавим, когда эндпоинты появятся; до тех пор в интерфейсе честно пишем, что
удаление окончательное.

Мелочь, но важная для порядка: у папки удаление каскадное, и в корзину должно уходить всё поддерево —
иначе восстановление папки вернёт пустую оболочку.

## 7. `POST /copy` — копирование файла и папки

Сейчас эндпоинта нет, `capabilities.copy = false`.

**Зачем.** Копирование — обычная операция файлового менеджера (у нас она на горячих клавишах), и в
объектном хранилище она серверная: `CopyObject` не гоняет байты ни через клиента, ни через API.
Без эндпоинта копия файла, лежащего только в облаке, означает «скачать гигабайты и залить те же
гигабайты обратно» — при том, что данные уже в бакете.

**Предлагаемая форма** (по аналогии с `/rename`):

```http
POST /api/storage/v1/copy
{ "projectId": "...", "fileId": "...",
  "destProjectId": "...",        // опционально, по умолчанию тот же проект
  "destFolderPath": "IN/копии",
  "name": "clip copy.mov",       // опционально, по умолчанию исходное имя
  "eventId": "..." }
→ { "file": { ...новая строка project_files с НОВЫМ fileId... } }
```

Для папки — рекурсивно, с журналированием по каждому созданному объекту (как в
`writeFileDelete`). Если рекурсия по папке дорога — начните с файла, папку мы обойдём на клиенте.

**Что нам от этого нужно на выходе:** новый `fileId` в ответе. Связывать копию с чем-либо руками не
нужно — новая строка каталога это и есть результат.

**Как ведём себя до эндпоинта:** копируем через себя (скачать → скопировать → залить как новый файл).
Работает, но платит трафиком за то, что уже лежит в бакете. Флаг `capabilities.copy` читаем, так что
переключение произойдёт само, как только он станет `true`.

## 8. Multipart — не срочно, но потолок жёсткий

Уже обсуждалось; фиксирую, чтобы список был полным. Одиночный presigned PUT ограничен **5 ГиБ** и не
возобновляется: обрыв на четвёртом гигабайте означает «начинай сначала».

Нужны `create` / `presign-part` / `complete` / `abort` плюс lifecycle-правило «abort incomplete
multipart uploads» на бакете, иначе брошенные части будут копиться и тарифицироваться.

С нашей стороны всё готово: выбор стратегии по размеру, поля `upload_id`/`parts_done` в очереди
передач, и **отказ до начала передачи**, если файл больше порога, а `capabilities.multipart = false`
(лучше внятная ошибка сразу, чем падение на четвёртом гигабайте из пяти).

Сейчас наши файлы меньше 5 ГиБ, так что это не блокер.

Чтобы не делать лишнего:

| | Почему |
|---|---|

## 12. Находки 2026-08-17 — служебные JSON-ы и физические имена

Разбор начался с простого наблюдения у пользователя: **папка `IN`, созданная в программе, на сайте
не появилась, а в `options` вместо двух файлов лежит пять с UUID в именах.** Копали с двух сторон —
локальный индекс клиента и код этого репозитория. Ниже только то, что подтверждено кодом.

Из четырёх находок **две чиним у себя** (12.1, 12.5) и **две просим у вас** (12.2, 12.3). Плюс
закрываем два вопроса из раздела 10 — ответы нашлись в коде.

### 12.1. Мы писали служебные JSON-ы не туда, куда сайт их читает — ЧИНИМ У СЕБЯ

Сайт читает `folderState.json` и `options.json` по **фиксированным** ключам:

```
lib/project-storage.ts:112  projectFolderStateKey → projects/{userId}/{projectId}/options/folderState.json
lib/project-storage.ts:120  projectOptionsKey     → projects/{userId}/{projectId}/options/options.json
```

А мы заливали их как обычные файлы, `presign → PUT → notify`. `/presign` в этом случае минтит
физический ключ `{uuid}-{имя}` (`app/api/storage/v1/presign/route.ts:88`):

```
projects/093025a9…/38b38e85…/options/34fc20c7-9627-41f3-9f20-512274ea3530-folderState.json
```

Следствие — **сайт наших настроек не видел никогда**, а мы не видели его: `optionsFileExists`,
`extractExposedOptions` и тумблер проекта смотрят только на канонический ключ. Два файла с одним
именем и разными ключами — это не «какая версия новее», это два разных объекта.

**Правильный канал у вас уже есть, и мы его не использовали:** `PUT/GET /api/storage/v1/sidecars`
(`kind: "raw"`, `sidecar: folder-state | options | description`, есть `ifMatch`). Он пишет ровно в
канонический ключ. Переводим клиент на него — от вас ничего не требуется.

**Одна просьба:** подтвердите, что `/sidecars` — единственный законный способ писать эти три файла,
а обычная заливка под этими именами не поддерживается. Тогда мы поставим у себя гейт и никогда больше
не пришлём их через `/notify`. Это же закрывает вопрос 6 из раздела 10 — формально заливка под
`options/` не запрещена, но она бессмысленна.

### 12.2. Список `options` в кабинете — это листинг бакета физическими именами

`listProjectServiceFiles` (`lib/project-storage.ts:478`) ходит `ListObjectsV2` по префиксу
`options/` и берёт имя как basename ключа:

```ts
// lib/project-storage.ts:498
const name = obj.Key.slice(obj.Key.lastIndexOf("/") + 1)
```

Отсюда `1c068f35-…-folderState.json` в интерфейсе. Два следствия:

1. **Имена физические.** Хелпер у вас уже написан — `logicalNameFromObjectKey`
   (`lib/storage/keys.ts:72`), но здесь не применён.
2. **Показывается любой объект под `options/`**, включая мусор от прошлых заливок. Пользователь видит
   не каталог, а бакет: у одного проекта `test 1` в списке пять «файлов» там, где файлов два.

**Просьба:** применить `logicalNameFromObjectKey` и, если возможно, показывать только известные
сайдкары (`folderState.json`, `options.json`, `description.md`) плюс `__stat/*.jsonl`. Остальное под
`options/` — техномусор, который пользователю показывать нечего.

### 12.3. `/notify` не возвращает `etag` и `contentHash`

`FILE_FIELDS` (`lib/storage/write-path.ts:35`) их не содержит. Для нас это значит: сразу после
**своей же** заливки мы не можем обновить в индексе версию, которая теперь лежит в облаке. Baseline
локальной копии становится новым, а версия каталога остаётся прежней — и файл до прихода следующей
дельты показывает значок «в облаке новее», хотя в облаке лежит ровно то, что мы только что отдали.
Ровно это пользователь и увидел на `options.json`.

Обходим у себя (после успешного `notify` пишем свой sha), но две колонки в `SELECT` решили бы это
честно, без допущения «в облаке то, что мы послали».

### 12.4. При 409 на `/notify` объект остаётся в бакете сиротой

`writeFilePut` → `assertNameFree` → 409 (`lib/storage/file-names.ts:112`). К этому моменту байты
**уже в бакете**: `presign` выписал новый ключ, PUT прошёл, и только `notify` отказал. Удалить этот
объект нам нечем — `delete` работает по `file_id`, а строки не появилось; удаления по ключу в API нет.
Значит каждый такой отказ — это оплаченные и никому не нужные байты навсегда.

**Просьба (на выбор, что вам ближе):** при конфликте имени либо переиспользовать существующую строку
(обновить её `s3_key`, прежний объект снести), либо удалить только что залитый объект перед тем как
вернуть 409.

Заодно: в бакете уже накопились сироты от этого механизма. Разовую чистку сделать можем только вы —
у нас нет ни листинга бакета, ни удаления по ключу.

### 12.5. `/delta` в поле `key` отдаёт s3-ключ — мы читали контракт неверно, ЧИНИМ У СЕБЯ

Мы считали, что журнал отдаёт логический ключ, и поэтому **не заполняли `s3_key`** из событий
дельты. Проверили по коду — для файлов `journal({ key: input.s3Key })`, то есть ключ настоящий;
логический он только у папок (`writeFolderCreate` → `logicalKeyForFile`, в payload `isFolder: true`).

Цена нашей ошибки была прямая: строка, впервые узнанная из дельты, оставалась без `s3_key` → при
следующей заливке в тот же путь мы не могли передать существующий ключ → `/presign` минтил новый →
прежний объект оставался в бакете сиротой (и, с появлением `assertNameFree`, ещё и ловил 409 —
см. 12.4). Различаем по `isFolder` и заполняем. От вас ничего не нужно.

### 12.6. Закрыт вопрос 1 из раздела 10: пустые логические папки `/tree` отдаёт

Проверено на живых данных: в локальном индексе лежат строки `IN` и `OUT` с `isFolder: true`, у
которых внутри нет ни одного файла. Вопрос снимаем.

Наша собственная ошибка рядом: часть путей создания папок в клиенте шла мимо `/mkdir` — папка
появлялась только на диске. Такая папка для каталога не существует: нет `file_id`, нет значка
синхронизации, нельзя переименовать и удалить через API. С этого и начался разбор. Чиним у себя.

### 12.7. Событие сайдкара в журнале без `fileId` — нам это удобно, менять не надо

`setProjectPaused` (`lib/project-automation.ts:69`) и ветка `options` в `sidecars/route.ts` пишут в
журнал событие с `payload: { name, folderPath }`, но без `fileId` — потому что строки в
`project_files` у сайдкаров нет. Раньше мы такие события считали неприменимыми и просили полный
`/tree`. Теперь используем их как сигнал «сайт тронул сайдкар — подтяни его через `/sidecars`».
Поведение хорошее, просьб нет.

## 13. Сделано 2026-08-17 — `options` стала обычной папкой

Раздел 12 закрыт целиком, но не так, как в нём просили. Вместо косметики в одном листинге снят сам
спец-случай: **служебная папка больше не исключение ни в одном месте кода.** Она приезжает из
`project_files` наравне с остальными, поэтому имена в ней логические, вложенность любая, а дубли
запрещены тем же уникальным индексом, что и везде (`project_files_unique_name_idx` по
`project_id, lower(folder_path), lower(name)`).

> ⚠️ Как и всё в этом документе, лежит в рабочем дереве. Пока не задеплоено — программа увидит
> прежнее поведение.

### 13.1. Что изменилось в поведении

| | Было | Стало |
|---|---|---|
| Листинг `options` | `ListObjectsV2` по префиксу, имя = basename ключа | выборка из каталога; спец-листинг удалён |
| Имена | физические (`1c068f35-…-folderState.json`) | логические |
| Подпапки | схлопывались на один уровень (`options/__stat` показывался как `options`) | настоящие, любой глубины |
| Дубли | два объекта с одним логическим именем показывались как два файла | одна строка на имя, инвариант в БД |
| Строки у сайдкаров | не создавались | создаются при каждой записи (`writeSidecarSync`) |
| Видимость | папка скрыта в кабинете, видна только админу | видна всем, как любая другая |
| `mkdir options` | 403 | разрешено |
| `/reindex` | префикс `options/` исключён из листинга | индексируется; исключены только `_catalog/` и `project-meta.json` |

### 13.2. Что это даёт клиенту

- **Сайдкары приезжают в `/tree` и `/delta` с `fileId`, `etag` и `contentHash`** — событие журнала
  теперь применимо к локальному индексу, полный `/tree` для этого не нужен. Пункт 12.7 закрыт с
  другой стороны: `fileId` в payload появился.
- **`/notify` отдаёт `etag` и `contentHash`** (пункт 12.3): `FILE_FIELDS` в `lib/storage/write-path.ts`
  их содержит, так что после своей заливки версия каталога известна сразу. Обходной путь с
  «пишем свой sha» можно снимать.
- **`GET /sidecars` отдаёт `etag`, `sizeBytes`, `lastModified`** рядом с `body`. Это и есть версия
  для `ifMatch`: расхождение облака с локальной копией теперь обнаруживается до записи.
- **`PUT /sidecars` с `ifMatch` отвечает 412**, а не 409 (было и то и другое одним кодом). 412 —
  «версия устарела, перечитай и реши, чья едет»; 409 остался за «имя занято».
- **409 на `/notify` больше не оставляет сирот** (пункт 12.4): объект удаляется перед отказом. Ссылок
  на ключ в этот момент заведомо нет, поэтому живой файл так снести нельзя. То же на пути записи с
  сайта (`writeR2PutFromBuffer`).
- **Разрешение расхождения** обеими кнопками работает уже сейчас: «скачать облачную» —
  `POST /presign` с `method: GET` на любой ключ под префиксом проекта; «залить локальную» —
  `POST /presign` с `method: PUT` и явным `s3Key` (объект перезаписывается на месте, `file_id`
  сохраняется), либо `PUT /sidecars` с `ifMatch` для трёх канонических.

### 13.3. Одно исключение, и оно узкое

`folderState.json`, `options.json`, `description.md` внутри `options` и сама папка `options` в корне
проекта **защищены от переименования, переноса и удаления** — 403. Причина ровно одна: сайт читает их
по фиксированному ключу, и уход с этого ключа тихо ломает тумблер проекта и его настройки при целом
и на вид исправном файле.

Всё остальное — как в любой папке: содержимое этих трёх файлов **перезаписывается свободно** через
`PUT /sidecars`, а прочие файлы и подпапки внутри `options` создаются, переименовываются,
переносятся и удаляются обычными роутами. Удаление, как везде, уходит в корзину на 30 дней.

Занять каноническое имя чужим файлом (переименовать что-то в `options/options.json`) тоже 403 — это
то же расхождение с другой стороны.

### 13.4. Гейт вместо договорённости (пункт 12.1)

`PUT /api/storage/v1/sidecars` — единственный законный канал для этих трёх файлов, и теперь это
проверяется, а не подразумевается: `/notify` на `folderPath: "options"` с каноническим именем и
неканоническим ключом отвечает **409** и убирает залитый объект. Ставить гейт у себя не нужно —
ошибка стала невозможной независимо от версии клиента.

### 13.5. Разовая консолидация бакета — обязательный шаг перед реиндексом

В бакете уже лежат двойники: канонический сайдкар и его `{uuid}-`копия с одним логическим именем.
Пока это не разобрано, `/reindex` по такому проекту упал бы на уникальном индексе и отменил бы всю
транзакцию.

`node scripts/storage-options-consolidate.mjs` (dry-run; `--apply` выполняет, `--project <id>`
ограничивает одним проектом) сводит группу к одному объекту: **живёт канонический ключ, содержимое
берётся самое свежее по дате**; если свежее лежало у `{uuid}`-двойника, его байты копируются на
канонический ключ. Строки каталога переводятся на выживший ключ, `file_id` сохраняется — для клиента
это тот же файл. Двойники с разным содержимым печатаются отдельной строкой: там выбор сделан за
пользователя, и это видно в логе.

Сам `/reindex` тоже больше не падает на таких группах: он дедуплицирует их на входе по тому же
правилу и сообщает число оставленных за бортом объектов в поле `shadowed`. Плюс он теперь **создаёт
строки-папок** для всего, что нашёл в бакете — до этого папка, впервые узнанная реиндексом, в дереве
не показывалась вообще (не только в `options`).
