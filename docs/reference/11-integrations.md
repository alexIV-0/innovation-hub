# 11 — Интеграции

Пять внешних систем: YouGile, Google OAuth, Resend, Web Push и парк
обрабатывающих машин. Плюс общие словари, которые синхронизируются между сайтом и
машинами.

---

## 1. YouGile — чат с командой

`lib/yougile.ts` — тонкий клиент поверх `fetch` к `https://yougile.com/api-v2`.
Библиотеки нет, схемы полей выверены по реальному
`ChatMessageListDtoBase` (https://yougile.com/api-json).

### Переменные

| Переменная | Зачем |
| --- | --- |
| `YOUGILE_API_KEY` | ключ. Его наличие = «интеграция настроена» (`isYouGileConfigured()`) |
| `YOUGILE_COMPANY_ID` | компания, в которой создаются чаты |
| `YOUGILE_BOT_USER_ID` | собственный пользователь сайта — по нему отсеивается эхо своих же сообщений |
| `YOUGILE_CHAT_MEMBER_IDS` | через запятую: кого добавлять в каждый новый групповой чат |
| `YOUGILE_WEBHOOK_SECRET` | shared secret для приёмника вебхука |

Список id пользователей компании — `node scripts/yougile-list-users.mjs`.
Настройка вебхука — `node scripts/yougile-setup-webhook.mjs` (нужен ещё
`APP_PUBLIC_URL`).

### Групповой чат проекта

Создаётся **лениво**, при первом сообщении. Заголовок:
`«имя проекта — email автора»`. Участники — из `YOUGILE_CHAT_MEMBER_IDS`.
Id пишется в `projects.yougile_chat_id`.

`ensureProjectYouGileChat()` не просто читает сохранённый id, а проверяет, что
чат **виден текущему ключу** и что в нём есть все настроенные участники. Причина:
после ротации ключа на Chat Bot старые `yougile_chat_id` указывают на чаты,
которых новый ключ не видит, и отправка **падает молча**. При 404/403 создаётся
новый чат.

### Исходящее: сайт → YouGile

`POST /api/projects/[id]/chat` пишет строку в `project_chat_messages`
(`sender_type: 'client'`) и отправляет в YouGile через
`deliverProjectMessageToYouGile()`. При 404/403 чат пересоздаётся и отправка
повторяется. `delivered` в строке показывает, доехало ли.

### Входящее: два канала, и оба нужны

#### Канал 1 — вебхук `POST /api/webhooks/yougile`

Авторизация — `?token=` против `YOUGILE_WEBHOOK_SECRET`. **Если секрет не
настроен, роут отказывает**, а не принимает молча неподтверждённые события.

Обработка:
1. распознать событие `chat_message-created` (нормализация имени: `event`,
   `eventType` или `type`, регистр и разделители не важны);
2. отсеять эхо своего сообщения по `botUserId`;
3. дедуп по `yougile_message_id` (уникальный частичный индекс);
4. найти проект по `chatId`; не нашёлся — это не наш чат, тихо выходим;
5. вставить строку `sender_type: 'team'`.

**Всегда отвечает 2xx** и только логирует сбои: YouGile ретраит на не-2xx, и
плохое или медленное событие не должно ронять приём сообщений. Нераспознанные
конверты пишутся в лог с `rawBody` — форма исходящего вебхука у YouGile нигде не
документирована, поэтому в типах оставлены несколько вероятных вариантов
написания полей.

#### Канал 2 — активное вытягивание `lib/project-chat-sync.ts`

Вебхук `chat_message-created` срабатывает **только на сообщения, отправленные
через REST API**. Сообщения, которые человек набрал прямо в приложении YouGile,
вебхук не вызывают вовсе.

> Проверено на живой переписке: из двенадцати сообщений вебхук доставил ровно
> одно — то, которое сайт сам отправил через API. Одиннадцать, набранных в
> интерфейсе YouGile, не дали ни одного вызова.

Поэтому сайт **тянет** сам: `syncProjectChatFromYouGile()` запрашивает всё, что
новее последнего известного сообщения, и пишет как `sender_type: 'team'`,
пропуская собственного бота.

Зовётся из двух мест:
- из `GET /api/projects/[id]/chat`, который браузер и так опрашивает раз в ~6 с;
- из фонового поллера `lib/chat-push-poller.ts` — раз в 30 с по всем проектам с
  привязанным чатом.

Фоновый поллер нужен ради push-уведомлений: без него они срабатывали бы только
пока у кого-то открыта страница.

### Ограничение, о котором надо помнить

**50 запросов в минуту на компанию**, и этот бюджет делят между собой:
- каждая открытая страница чата (опрос раз в ~6 с),
- фоновый поллер (раз в 30 с × число проектов с чатом).

На сегодняшнем масштабе хватает. При росте числа связанных проектов —
удлинять интервалы, разносить проекты по тикам, батчить.

### Что ещё не подключено

`/api/feature-suggestions` и `/api/video-orders` помечены `TODO(yougile)`:
валидация и сборщики текста заявки готовы, доставки нет, роуты отдают 503.

## 2. Google OAuth

Полностью описан в [06 — Аутентификация](./06-auth-and-access.md#2-google-oauth).
Кратко: `lib/google-oauth.ts`, три запроса руками, `GOOGLE_CLIENT_ID` +
`GOOGLE_CLIENT_SECRET`. Обе кнопки («Continue with Google» на `/login` и
`/register`) появляются только когда обе переменные заданы.

Redirect URI собирается из запроса — nginx обязан пробрасывать
`X-Forwarded-Proto`, иначе на продакшене соберётся `http://`.

### Google Drive — историческая интеграция

`lib/google-drive.ts` (~700 строк, тянет `googleapis`) **не импортируется
нигде**. То же у `lib/project-drive.ts` и `lib/provision-drive.ts`. Переменные
`GOOGLE_DRIVE_*` в `.env.example` помечены «legacy one-time migration only».

Следы в живом коде: колонки `users.drive_folder_id`, `projects.drive_folder_id`,
таблица `project_media`, имена роутов `/api/projects/[id]/drive/*` (они работают
с R2, а не с Drive). `GET /api/projects` всегда отдаёт `driveConfigured: false`.

## 3. Resend — письма

`lib/mail/send.ts` + `lib/mail/templates.ts`.

| Переменная | Зачем |
| --- | --- |
| `RESEND_API_KEY` | без него отправка **пропускается** с предупреждением в лог, а не падает |
| `RESEND_FROM` | подтверждённый отправитель; по умолчанию `InnoHub <onboarding@resend.dev>` |
| `APP_PUBLIC_URL` | база ссылок в письме; фолбэк — `https://ffworks.pro` |

Два письма, оба про расшаривание проекта:

| Функция | Когда |
| --- | --- |
| `sendProjectAccessGrantedEmail` | доступ выдан существующему пользователю. Ссылка ведёт прямо в проект |
| `sendProjectInviteWithPasswordEmail` | приглашён человек, у которого аккаунта не было: письмо несёт email и временный пароль, аккаунт помечается `must_change_password` |

Каждое письмо отправляется и как HTML, и как plain text. В тексте письма
проговаривается роль и что она даёт (`shareRoleCopy`).

Возвращается `MailResult = {ok:true, id?} | {ok:false, error}` — расшаривание не
откатывается из-за неотправленного письма.

## 4. Web Push — уведомления о сообщениях

`lib/push.ts` + `public/sw.js`.

| Переменная | Зачем |
| --- | --- |
| `VAPID_PUBLIC_KEY` | отдаётся браузеру через `GET /api/push/vapid-public-key` |
| `VAPID_PRIVATE_KEY` | подпись |
| `VAPID_SUBJECT` | `mailto:` владельца |

Генерация: `node -e "console.log(require('web-push').generateVAPIDKeys())"`.

Поток:
```
браузер: GET /api/push/vapid-public-key
       → pushManager.subscribe()
       → POST /api/account/push-subscription  { endpoint, keys }
                                                    ↓
                                          push_subscriptions

появилось сообщение команды (sync из YouGile)
       → sendPushToUser(ownerId, {title, body, url})
       → всем подпискам пользователя параллельно
```

Особенности:
- **одна нотификация на вызов sync, а не на сообщение**: пачка накопившихся
  ответов не спамит устройство;
- подписка, про которую push-сервис ответил 404/410 (данные очищены, браузер
  удалён), **удаляется автоматически**;
- любая другая ошибка по одной подписке логируется и игнорируется — одно мёртвое
  устройство не блокирует остальные;
- если VAPID не настроен, `sendPushToUser` просто выходит.

Service worker минимальный: только `push` и `notificationclick`, без офлайн-кеша.
`notificationclick` ищет уже открытое окно с нужным путём и фокусирует его,
иначе открывает новое.

## 5. Парк обрабатывающих машин

Полностью — [08 — Конвейер](./08-pipeline.md) и
[06 — Токены](./06-auth-and-access.md#4-машинные-токены). Кратко:

| | `mch_…` | `rc_…` |
| --- | --- | --- |
| Кто создаёт | пользователь в профиле | админ в `/admin/remote-access` |
| Модель | один токен, много машин | один токен, один компьютер |
| Идентичность машины | `machineUuid`, машина заводит себя сама | из токена |
| Поверхность | `/api/storage/v1/*` (REST) | `POST /api/v1` (RPC) |
| Заливщик для атрибуции | да | **нет** |
| Ротация | нет, только отзыв | есть |

Живая документация машинного API — `/admin/remote-access/api`, рендерится из
`lib/machine-api/catalog.ts`. Реестр (`registry.ts`) при загрузке в dev-режиме
**громко сверяется с каталогом** и пишет расхождения в обе стороны: экшен без
карточки снаружи выглядит как отсутствующая возможность, карточка без экшена —
как существующая.

## 6. Общие словари

`docs/SETTINGS_SYNC.md`. Общая конвенция сайта и всех машин: типы файлов с
расширениями, цвета типов нод и типов данных, пользовательские маски путей.

### Хранение

`automation_settings` — **синглтон**: словарь принадлежит системе обработки, а не
клиенту, который заливает файлы.

Четыре домена (`SETTINGS_DOMAINS`): `fileType`, `nodeType`, `dataType`,
`pathPattern`.

Запись домена (`SettingsEntry`):

```ts
{ name: string, path: string[], color: string | null, isDefault: boolean }
```

- `path` значит разное: расширения у `fileType`, сегменты маски у `pathPattern`,
  у остальных пуст;
- `id` **не хранится**: у дефолтов он человекочитаемый (`video`), у
  пользовательских — nanoid, то есть на второй машине другой. Идентичность во
  всей системе по имени: графы ссылаются на тип как `searchType: "video"`,
  `getFileTypeByExt` ключует по имени, десктоп сливает дефолты по имени;
- домен — **массив**, а не объект: порядок значим, `getFileTypeByExt` возвращает
  первое совпадение, поэтому расширение, попавшее в два типа, достаётся верхнему.

### Оптимистическая блокировка

`revision` растёт на **каждую** запись, даже если содержимое не изменилось.
Запись — `UPDATE … WHERE revision = $base`; не сошлось → 409 с актуальным
документом. Это счётчик версии, а не хеш состояния.

### Три поверхности, одна логика

`lib/settings-endpoint.ts` — общая логика; роуты остаются тонкими: их дело —
авторизоваться своим способом и разобрать тело.

| Поверхность | Кто ходит |
| --- | --- |
| `GET/PUT /api/storage/v1/settings` | десктоп (`mch_…`) |
| экшены `getSettings` / `putSettings` на `POST /api/v1` | машины парка (`rc_…`) |
| `GET/PATCH /api/admin/settings` | браузер, страница настроек конвейера |

Права: **читать** может любой авторизованный (редактору нод нужен список типов,
чтобы показать его на выбор), **писать** — админ или машина.

### Сидирование

`seedDefaultSettings()` вызывается один раз при старте процесса из
`instrumentation.ts`. Идемпотентно и наливает **только пустые** домены — поэтому
безопасно на каждом старте и не откатывает правки пользователя. Вызов без
`await`: сид не должен задерживать старт и тем более ронять процесс, если база
ещё не поднялась.

Типы и константы вынесены в отдельный файл `lib/settings-types.ts` — их
импортируют и серверный репозиторий, и клиентские компоненты, а лежи они в
`repositories/automation-settings.ts`, любой импорт значения из клиента утянул бы
в бандл `pg`.

### Подписи для интерфейса

`DOMAIN_LABELS` в `lib/settings-types.ts` держит **ключи** подписей, а сами
тексты живут в `components/admin/admin-dict.ts`: они переводятся, а этот файл про
переводы не знает и знать не должен.
