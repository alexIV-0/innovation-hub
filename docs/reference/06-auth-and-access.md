# 06 — Аутентификация и доступ

---

## 1. Сессия пользователя

| Параметр | Значение |
| --- | --- |
| Транспорт | cookie `inhub_session` |
| Формат | JWT, HS256, библиотека `jose` |
| Полезная нагрузка | `sub` = userId, `role`, `email` |
| Срок | 7 суток (`SESSION_TTL_SECONDS`) |
| Cookie | `httpOnly`, `sameSite: "lax"`, `path: "/"`, `secure` только в production |
| Секрет | `SESSION_SECRET`. В dev при отсутствии — предсказуемый фолбэк; в production бросает |

Секрет кешируется в закодированном виде, но кеш инвалидируется при смене
переменной — нужно для HMR.

Пароли: `bcryptjs`, 10 раундов. `password_hash` может быть `NULL` —
у OAuth-аккаунтов.

### Лестница ролей

`USER < ADMIN < SUPERADMIN` — `lib/admin-roles.ts`. **Чистый модуль**: без базы и
без `next/server`, поэтому его импортируют и роуты, и интерфейс — как
`lib/project-roles.ts` для прав на проект.

| Функция | Что отвечает |
| --- | --- |
| `roleAtLeast(role, minimum)` | «не ниже чем». Принимает `string`, неизвестное значение = отказ |
| `isElevated(role)` | «это админский аккаунт вообще»: вход в `/admin`, обход владения в хранилище, общая очередь у машины |
| `isSuperAdmin(role)` | раздача доступа: смена ролей и действия над другим админом |

Сравнивать роль литералом (`role === "ADMIN"`) **нельзя**: такая проверка
отсекает суперадмина, а на машинных путях ещё и ломает парк — `mch_`-токен берёт
роль владельца живым JOIN'ом, и повышение человека молча меняет поведение его
машины. Единственное намеренное исключение — `role: "ADMIN"` в
`authFromRemoteComputerToken`: это не сравнение, а выдача роли `rc_`-токену.

### Кто кем управляет

| Действие | ADMIN | SUPERADMIN |
| --- | :-: | :-: |
| Заводить, править, блокировать и удалять `USER` | ✅ | ✅ |
| Править собственный профиль и пароль | ✅ | ✅ |
| Любое действие над `ADMIN` или `SUPERADMIN` | — | ✅ |
| Менять роль кому угодно | — | ✅ |
| Заводить аккаунт сразу с ролью `ADMIN`/`SUPERADMIN` | — | ✅ |
| Менять **свою** роль | — | — |

Правило одно: **админ управляет только теми, кто ниже него; равного и старшего не
трогает.** Та же симметрия, что у `canManageMember` в правах на проект (§7).
Исключение — собственный аккаунт: правка своего имени и пароля к управлению
чужими аккаунтами не относится и остаётся доступной.

Создание админа гейтится наравне с повышением (`POST /api/admin/users`): иначе
запрет обходился бы заведением нового аккаунта вместо повышения старого.

### Два инварианта на удаление и блокировку

| Инвариант | Функция | Зачем |
| --- | --- | --- |
| Хотя бы один активный аккаунт с доступом в админку | `countActiveAdmins` | иначе `/admin` недостижим |
| Хотя бы один активный **суперадмин** | `countActiveSuperAdmins` | иначе роли и права некому раздать |

Второй первого не заменяет: «админка достижима» выполняется и одними админами.
Проверяются оба — при понижении роли, блокировке, удалении и при самоудалении
через кабинет (`DELETE /api/account`).

## 2. Google OAuth

`lib/google-oauth.ts` — три запроса руками, без библиотеки.

```
GET /api/auth/google?next=/account
  → генерирует state (24 случайных байта)
  → кладёт state и next в cookie с path=/api/auth/google, TTL 10 минут
  → 302 на accounts.google.com

GET /api/auth/google/callback?code=&state=
  → сверяет state с cookie          → не сошлось: /login?error=google_state_mismatch
  → обменивает code на access_token
  → тянет профиль
  → требует email_verified           → нет: /login?error=google_email_unverified
  → ищет по (provider, sub)
      найден  → вход
      нет → ищет по email
              найден  → привязывает Google к существующему аккаунту,
                        пароль НЕ затирается — оба способа входа работают
              нет → создаёт аккаунт без пароля
  → ставит сессию, чистит OAuth-cookie, редирект на next
```

`next` проверяется всегда: должен начинаться с `/` и не с `//`, иначе `/`.
`redirect_uri` собирается из запроса — поэтому nginx обязан пробрасывать
`X-Forwarded-Proto`, иначе на продакшене соберётся `http://`.

Коды ошибок на `/login?error=`: `google_unconfigured`, `google_denied`,
`google_invalid_response`, `google_state_mismatch`, `google_token_failed`,
`google_email_unverified`, `google_link_failed`, `google_create_failed`,
`account_inactive`.

## 3. Гварды в коде

| Функция | Модуль | Возвращает |
| --- | --- | --- |
| `getCurrentUser()` | `lib/admin-auth.ts` | `UserRecord \| null`. Обёрнута в `React.cache` — layout и страница в одном рендере платят один запрос, а не два |
| `requireUserApi(request)` | `lib/admin-auth.ts` | `{userId, email, role}` или `NextResponse` 401/403 |
| `requireAdminApi(request)` | `lib/admin-auth.ts` | `{userId, email, role}` или 401/403. Пускает `ADMIN` и `SUPERADMIN` |
| `requireStorageApi(request)` | `lib/storage/auth.ts` | `StorageApiAuth` — сессия, `mch_…` или `rc_…` |
| `authenticateComputerToken(token)` | `lib/storage/auth.ts` | только `rc_…`; для `POST /api/v1` |

Идиома у всех одна: гвард возвращает **либо данные, либо готовый ответ**, и роут
пишет `if (auth instanceof NextResponse) return auth`. Это позволяет не бросать
исключения ради 401.

## 4. Теги прав (capabilities)

Лестница отвечает, пускать ли в админку и кто кем управляет. **Чем человек
занимается** — отвечают теги: `lib/admin-capabilities.ts`, тоже чистый модуль.

Админы различаются не глубиной прав, а направлением работы: один занимается
акциями и подарками, другой по запросу разбирает чужие проекты. Это не
«выше/ниже», это разные комнаты, и лестницей такое не выражается.

> **Теги раздают доступ к работе, но никогда — к раздаче доступа.**

Ни один тег не даёт выдавать теги, менять роли и трогать другого админа — это
свойство роли `SUPERADMIN`. Тега вида `capabilities.grant` в списке нет и быть не
должно: с ним админ дотянулся бы до суперадмина через сам механизм тегов.

| Тег | Что открывает |
| --- | --- |
| `users.read` | список людей, `/admin/users` на чтение |
| `users.manage` | заводить, править, блокировать и удалять **обычных** пользователей |
| `content.manage` | видео, идеи, загрузка медиа, предложения тегов |
| `pipeline.operate` | конвейер целиком; список компьютеров и **отзыв** токена |
| `settings.write` | правка общих словарей (`PATCH /api/admin/settings`) |
| `machines.manage` | **выпуск и ротация** `rc_`-токенов |
| `projects.access` | файлы чужих проектов: `/api/media/*`, обходы владения в `lib/storage/*` |
| `statistics.view` / `statistics.import` | статистика и её загрузка пачкой |
| `visitors.view` | аналитика посещений |
| `billing.manage` | баланс и акции (см. BILLING_AND_TRIAL_PLAN.md) |
| `audit.view` | журнал действий |

Выпуск и отзыв токена — разные теги намеренно. Выпуск `rc_` это выдача кредов с
доступом к общей очереди, редкая операция. Отзыв — стоп-кран, он нужен ровно
тогда, когда что-то пошло не так, и держать его за отдельным человеком значит
держать стоп-кран за стеклом.

`hasCapability(role, granted, needed)`: суперадмину `true` без проверки (строк в
таблице у него нет и не должно быть — иначе второй источник правды), всем ниже
админа — `false` независимо от содержимого, чтобы тег, оставшийся у понижённого
аккаунта, ничего не открывал.

### Хранение

`admin_capabilities (user_id, capability, granted_by, granted_at)`. Таблица, а не
массив в `users`: `granted_by` отвечает на первый вопрос, который задаёт
суперадмин, увидев неожиданное. Читается отдельным запросом, а не джойном в
`PUBLIC_USER_FIELDS` — те же поля стоят в `RETURNING` у пяти мутаций.

Понижение до `USER` или повышение до `SUPERADMIN` **очищает** теги
(`clearCapabilities`): иначе они всплыли бы обратно при повторном повышении,
молча вернув доступ, которого никто не выдавал.

### Обязательный аргумент гварда

```ts
const auth = await requireAdminApi(request, "billing.manage")
```

Без умолчания — это единственное, что защищает модель от гниения: новый роут в
`/api/admin/*` без решения о теге не соберётся. С умолчанием через полгода
половина роутов оказалась бы «доступна всем», и никто бы не заметил.

Три слоя, и они дублируют друг друга намеренно: пункт меню
(`visibleNavItems`), гвард страницы (`requireCapabilityPage`, редирект на
`/admin`) и гвард API. Меню — про удобство, гварды — про доступ; полагаться на
скрытую кнопку как на защиту нельзя.

Обзор `/admin` — единственная страница без тега: туда попадает каждый, кто вошёл
в админку. Блоки внутри неё скрываются по тегам, а не показывают нули: «0 видео»
человеку, которому видео не видны, — не пустая страница, а неверная.

Раздача самих тегов живёт на `/admin/access/roles` — отдельной страницей, а не
пунктом в контекстном меню списка людей. Причина конкретная: пункт показывался
только у строк с ролью `ADMIN`, а сразу после миграции таких строк нет ни одной —
инструмент нельзя было увидеть, пока им уже не воспользовался.

Внутри раздела действие может требовать **другой** тег, чем сам раздел. Такие
кнопки прячутся через `can()` из контекста админки — кнопка, которая
гарантированно вернёт 403, хуже отсутствующей:

| Раздел открыт по | Действие внутри требует |
| --- | --- |
| `users.read` | заводить, править, блокировать и удалять — `users.manage` |
| `statistics.view` | загрузка пачкой — `statistics.import` |
| `pipeline.operate` | выпуск и ротация `rc_`-токена — `machines.manage` |
| `pipeline.operate` | правка общих словарей — `settings.write` |

### Теги и машины

**На машинных путях теги не спрашиваются вообще.** Программа авторизуется
протоколом. Отсюда `canReachAnyProject(auth)` в `lib/storage/auth.ts` — одна
функция на все места, где раньше стояло `auth.role === "ADMIN"`, и порядок в ней
значим: **сначала машина, потом тег**.

```ts
if (isMachineAuth(auth)) return isElevated(auth.role)
return hasCapability(auth.role, auth.capabilities, "projects.access")
```

Особенно это важно там, где ветки человека и машины **не разделены**:
`requireOwnedProjectAccess`, `project-catalog.ts`, `project-mutations.ts` —
голая проверка тега там уронила бы обработку у всего парка.

## 5. Журнал действий

`admin_audit_log` + `lib/repositories/admin-audit.ts`, читается на `/admin/audit`
по тегу `audit.view`. Пишется **всегда**, независимо от того, есть ли у кого-то
тег на чтение.

`recordAuditEvent` **никогда не бросает**: журнал — наблюдение за действием, а не
его часть, и упавшая вставка не должна ронять то, что уже произошло.

Список действий закрытый и лежит в `lib/audit-actions.ts` — отдельно от
репозитория, чтобы страница журнала могла импортировать его, не утянув `pg` в
браузерный бандл (та же причина, что у `lib/settings-types.ts`).

Пишутся: создание, правка, блокировка и удаление аккаунта, смена роли, сброс
чужого пароля, выдача и отзыв тега, выпуск, ротация и отзыв `rc_`-токена, правка
словарей, удаление проекта.

Удаление проекта логируется **независимо от того, человек это или машина**
(`meta.via`). Это не ограничение программы — её права мы не трогаем; это
единственное необратимое действие, которое она делает штатно, и вопрос к нему
всегда «когда и по чьей задаче», а не «кто разрешил».

`actor_email` продублирован строкой: актора могут удалить, а запись «кто это
сделал» обязана пережить его аккаунт.

### Почему в токене лежит роль

Чтобы `proxy.ts` мог отсечь не-админа от `/admin` без обращения к Postgres.
Авторитетная проверка (`is_active`, актуальная роль) делается один раз в
`app/admin/layout.tsx` и в каждом `/api/admin/*`. Разжалованный админ отлетает
на первом же запросе, но за навигацию по админке не платится round-trip в базу.

## 6. Машинные токены

Два вида, оба хранятся только хешем (SHA-256, `hashMachineToken`).

### `mch_…` — токен пользователя

Создаётся в `/account/profile` → `POST /api/account/machine-tokens`. Сырое
значение показывается **один раз**.

- Модель — «один токен, много машин»: одним токеном могут ходить несколько
  машин, каждая присылает свой `machineUuid` и заводит себя сама.
- Может быть заскоупен на один проект (`machine_tokens.project_id`): попытка
  обратиться к другому → 403 «Machine token is scoped to another project».
- Роль наследует владельца, и наследует её **живым JOIN'ом при каждом запросе**,
  а не слепком на момент выдачи. Под админским токеном машина видит общую
  очередь, под обычным — только проекты своего владельца. Это граница доверия, а
  не деталь реализации.
- Следствие, важное при любой правке ролей: повышение или понижение человека
  сразу меняет поведение его машин. Поэтому машинные пути спрашивают
  `isElevated`, а не конкретную ступень.
- `last_used_at` обновляется при каждой авторизации.
- Отзыв токена **отзывает и машины под ним**: машина существует в списке только
  как «кто обращался этим токеном». Машины помечаются отозванными, а не
  удаляются — та же машина по своему UUID заведётся заново под новым токеном.
- Отозвать может владелец (`DELETE /api/account/machine-tokens`) и админ с
  `pipeline.operate` (`DELETE /api/admin/machines/[id]`, меню на строке токена в
  `/admin/remote-access`). Второе — потому что страница показывает токены всех
  аккаунтов: видеть чужой брошенный токен и не мочь его снять означало бы
  ходить за этим под чужим логином.

### `rc_…` — токен компьютера

Создаётся админом в `/admin/remote-access`. Один токен = один компьютер.
Есть ротация (`POST /api/admin/computers/[id]/rotate-token`).

Особенность, важная для статистики: **машина парка заливщиком не считается**.

```
actorFromAuth(auth) → { userId, isUploader: auth.computerId == null }
```

`userId` машины `rc_` — это `remote_computers.created_by`, то есть админ,
регистрировавший компьютер. Если бы её запись перетирала `uploaded_by`,
`description.contact` следующей задачи переехал бы на этого админа.

## 7. Права на проект

Лестница ролей — `lib/project-roles.ts`. **Чистый модуль**: без обращений к базе
и без `next/server`. Поэтому его же импортирует интерфейс
(`components/account/workspace/access.ts`) — матрица одна, а не по копии на слой.

```
viewer (1) → editor (2) → full (3) → owner (4)
```

`owner` — не роль в `project_members`, а сам `projects.user_id`.
Почти все проверки — «не ниже чем», поэтому `full` автоматически проходит там,
где хватает `editor`.

### Матрица прав

| Действие | viewer | editor | full | owner |
| --- | :-: | :-: | :-: | :-: |
| Читать проект, дерево, описание, чат; скачивать | ✅ | ✅ | ✅ | ✅ |
| Писать в чат | — | ✅ | ✅ | ✅ |
| Заливать, создавать, переименовывать, удалять, перемещать файлы | — | ✅ | ✅ | ✅ |
| Параметры обработки, пауза, состояние папок | — | ✅ | ✅ | ✅ |
| Переименовать проект, править короткое описание | — | — | ✅ | ✅ |
| Расшаривать дальше, менять роли, отзывать доступ | — | — | ✅ | ✅ |
| Отправить в архив / вернуть из архива | — | — | ✅ | ✅ |
| **Удалить проект в корзину, восстановить, переносить между клиентами** | — | — | — | ✅ |

Удаления проекта нет ни у кого, кроме владельца, даже у полного доступа. Полный
доступ — это право распоряжаться **работой** в проекте, а не право убрать саму
папку у того, кто её завёл.

### Делегирование

| Функция | Правило |
| --- | --- |
| `canGrantRole(actor, target)` | полный доступ выдаёт любую роль, включая полный: цепочка делегирования не ограничена — решение владельца продукта |
| `canManageMember(actor, target)` | владелец — у всех. Полный доступ — только у `viewer` и `editor`: равного себе он не трогает, иначе двое приглашённых могут вычеркнуть друг друга из проекта, который завёл не они |

## 8. Две функции `requireProjectAccess` — и это не ошибка

| | `lib/project-access.ts` | `lib/storage/auth.ts` |
| --- | --- | --- |
| Для чего | роуты кабинета (`/api/projects/*`) | машинный протокол (`/api/storage/v1/*`, `/api/v1`) |
| Принимает | `userId` | `StorageApiAuth` |
| Знает про машинные токены | нет | да |
| Нет доступа вовсе | **404** | **404** |
| Доступ есть, роль ниже | **403** с внятным текстом | **404** |

Разница ответов намеренная. В кабинете: чужой проект — 404, чтобы не
подтверждать сам факт его существования; своя роль ниже нужной — 403, потому что
человек проект видит и должен понять, почему действие не прошло, а не решить, что
проект исчез. В машинном протоколе оба случая 404 — контракт
`/api/storage/v1/*` менять нельзя.

Роль обе считают **одним и тем же кодом** — `lib/project-roles.ts`.

### Расшаривание на машинные токены не распространяется

`requireProjectAccess` из `lib/storage/auth.ts` для `mch_`/`rc_` проверяет только
владение (`findOwnedProject`), кроме случая `role === ADMIN`. Машина, ходящая под
токеном пользователя, не увидит проектов, которые ему расшарили.

## 9. Права в интерфейсе

Два слоя, и они перемножаются:

1. **Потолок зоны** — `source.can` в `WorkspaceSource`. Кабинет разрешает работу
   с файлами, админский «Конвейер» — почти ничего, кроме описания и паузы.
2. **Роль в проекте** — `capabilitiesForRole()` из матрицы `permissionsFor`.

```
право = потолок зоны  И  то, что даёт роль
```

Роль не поднимает потолок зоны (в «Конвейере» загрузки нет ни у кого), зона не
отменяет ограничение роли (читателю расшаренного проекта нельзя показывать кнопки
владельца).

`projectRole(project)` переводит карточку проекта в роль: свой проект → `owner`;
расшаренный без внятной роли → `viewer`, потому что неизвестное право не может
быть больше самого узкого.

## 10. Доступ к медиафайлам

`/api/media/[...key]` — единственный путь к байтам из браузера.

1. Ключ декодируется посегментно, `..` отбрасывается **до и после** декодирования,
   `/` внутри сегмента запрещён.
2. `isAllowedMediaObjectKey(key)` — жёсткий белый список префиксов:
   `projects/{uuid}/{uuid}/…`, `admin/`, `feature-suggestions/`, legacy
   `innohub/`, `ffworks/`. Без этого любой вызывающий мог бы подписать URL на
   любой объект бакета, включая соседей другого приложения.
3. Для ключей проектов — обязательна сессия; админ открывает любой; обычный
   пользователь — только `projects/{свой userId}/…`. Для legacy-ключей владение
   проверяется по базе (`findFileByS3Key`).
4. Отдача: 307 на presigned GET (TTL час, `Cache-Control: private, max-age=1800`)
   либо, с `?raw=1`, стрим тела (оптимизатор картинок Next не следует за 307).

## 11. Rate limiting

`lib/rate-limit.ts` — `Map` в памяти процесса, окно + счётчик.

| Где | Лимит |
| --- | --- |
| `/api/feature-suggestions` | 3 / 10 минут на IP |
| `/api/video-orders` | 3 / 10 минут на IP |
| `/api/projects/[id]/chat` | есть, см. роут |

IP берётся из `X-Forwarded-For` → `X-Real-IP` → `CF-Connecting-IP`. Работает,
только пока инстанс один. В самом файле помечено: заменить на Redis/KV при росте.

## 12. Что защищено, а что нет

✅ Пароли хешируются, сырые токены не хранятся.
✅ Session cookie `httpOnly` + `sameSite=lax`.
✅ CSRF-риск снижен `sameSite=lax` (но явных CSRF-токенов нет).
✅ Валидация zod на каждом входящем теле.
✅ Прокси медиа с белым списком префиксов и защитой от traversal.
✅ Санитайз markdown **на рендере**, а не только при сохранении.
✅ Honeypot-поле `website` в публичных формах.
✅ Проверка `state` в OAuth.
✅ Вебхук YouGile — shared secret; при отсутствии секрета **отказывает**, а не
   принимает молча.
✅ Мягкое удаление везде, где потеря данных необратима.
✅ Журнал действий админов: роли, теги, аккаунты, токены, словари, удаление
   проектов. Запись не может уронить действие, которое логирует.

🔧 Rate limit только в памяти процесса.
🔧 `typescript.ignoreBuildErrors: true` — типовые ошибки не блокируют сборку.
🔧 CSP, HSTS и прочие security-заголовки не настроены ни в Next, ни в nginx.
🔧 `SESSION_SECRET` в dev имеет предсказуемый фолбэк.
